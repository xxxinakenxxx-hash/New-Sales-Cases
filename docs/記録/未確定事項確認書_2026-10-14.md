- A4印刷・PDF出力はMVP必須
- PDFは1事例単位。複数事例一括出力はMVP対象外
- 匿名共有版はMVP対象外

- 旧データの初期移行は行わない

- 構造化検索 + 全文検索をMVP基本とする
- ベクトル検索はMVP必須ではない
- 公開済み事例の改訂中も旧公開版を維持する

## 4. ユーザー確認が必要な事項

### U-01 権限の実運用

確認したいこと:

営業担当者・営業管理者・管理者が、他人の案件にどこまで触れてよいか。

推奨案:

- salesperson: 自分の案件を作成・編集・事実確認・編纂確認・公開・公開停止できる
- manager: 自分の案件に加え、管轄案件を閲覧できる。MVPでは他人の案件を直接編集しない
- admin: 全案件を閲覧し、公開停止・アーカイブ等の管理操作ができる
- sysadmin: admin権限 + システム設定。通常の営業内容を勝手に書き換える用途には使わない

確認ポイント:

1. managerは管轄案件を「閲覧のみ」でよいか
2. salesperson本人が公開まで行ってよいか
3. adminは他人の案件本文を直接編集できる必要があるか

工程表作成前: 必須

### U-02 managerの「管轄」の単位

確認したいこと:

managerが見られる案件範囲を何で決めるか。

推奨案:

所属拠点・部門を利用者マスターに持たせ、managerは自分と同じ管理単位の案件を閲覧する。

個別案件ごとの手動割当はMVPでは行わない。

工程表作成前: 必須

### U-03 公開停止・アーカイブの操作権限

確認したいこと:

一度公開した事例を誰が非公開化できるか、作成途中案件を誰がアーカイブできるか。

推奨案:

- 作成者: 自分の案件を公開停止・アーカイブ可能
- manager: 管轄案件は閲覧のみ
- admin: 全案件を公開停止・アーカイブ可能

工程表作成前: 必須

## 5. ChatGPT側で設計・技術選定してよい事項

以下はユーザーへ製品名だけを投げて選ばせず、旧資産調査・要件適合・コスト・保守性を比較してChatGPTが推奨案を作る。

### T-01 アプリ基盤・ホスティング

未確定:
- フロントエンド
- バックエンド
- ホスティング
- デプロイ方式

決定方法:
旧コード資産調査後、新要件に対してGAS継続と新構成を比較する。

### T-02 DB・保存方式

未確定:
- DB製品
- source / fact / compilation / publication / logs の物理保存方式
- transaction方式

決定方法:
履歴、競合、全文検索、権限、添付資料との相性で比較する。

### T-03 AI provider / model

未確定:
- provider
- model
- API
- 構造化出力方式
- 再試行方式

決定方法:
日本語品質、長文コンテキスト、構造化出力、コスト、速度、機密情報取扱いで比較する。

### T-04 認証方式

未確定:
- 認証サービス
- user / role / branch の取得方法

決定方法:
社内アカウント基盤との適合を確認して決める。

U-01/U-02の業務権限を先に確定する。

### T-05 添付資料

未確定:
- PDF / JPEG / PNG / DOCX / XLSX / TXT 等の対応範囲
- ファイルサイズ上限
- 1案件あたり件数上限
- OCR / document parser
- 物理ストレージ
- 抽出テキスト保持方式

推奨方針:
MVPでは実務で使う主要形式を優先し、形式を増やすために読取品質を落とさない。

### T-06 検索実装

確定:
構造化検索 + 全文検索。

未確定:
全文検索エンジンと物理索引方式。

ベクトル検索はMVPでは実装しない。

### T-07 A4/PDF

確定:
1事例単位のA4印刷・PDFはMVP必須。

未確定:
- 表裏の具体レイアウト
- PDF renderer
- ブラウザ印刷との役割分担

決定方法:
旧Gemの良かった情報構成を参考に、画面とは別の印刷ViewModelとして設計する。

### T-08 画面UI詳細

機能画面S-01〜S-10と主要操作は確定済み。

未確定:
- 具体レイアウト
- スマートフォン配置
- 質問バッチの見せ方
- fact確認の情報密度
- A4/PDFプレビュー導線

画面モック作成時に確定する。

### T-09 管理マスター

未確定:
具体的にどのマスターを管理画面から編集可能にするか。

推奨方針:
MVPで実際に業務上変更が必要なものだけを管理対象とし、fact domainのような設計項目を自由追加マスターにしない。

### T-10 途中離脱判定日数

確定:
途中離脱はイベントではなく、一定期間進行がない案件から算出する派生指標。

未確定:
標準日数。

推奨案:
初期値14日。運用開始後に変更可能とする。

工程表作成を止める事項ではなく、分析工程までに確定すればよい。

### T-11 旧コード再利用

未確定:
旧「機械販売事例まとめアプリ」のどのコードを再利用するか。

決定方法:
新正本を基準に、旧コードを再利用 / 改修 / 廃止 / 新規 / 未確認へ分類する。

新正本を旧コードへ合わせない。
