# 開発運用ルール

更新日: 2026-10-14

## 1. 目的

本書は「新販売事例」の開発における、正本管理、ChatGPT、Claude Code、ユーザーの役割分担、進捗記録、実装指示、確認、完了判定の運用ルールを定める。

## 2. 正本管理

- GitHubリポジトリ `xxxinakenxxx-hash/New-Sales-Cases` を本プロジェクトの管理場所とする。
- 正本文書はMarkdownで管理する。
- 設計・仕様の正本は `docs/正本/` に置く。
- Google Drive上の旧Word、旧PDF、ローカルPC上のコピーは、新プロジェクトの正本にしない。
- 旧プロジェクト資料は参考資料としてのみ扱う。
- 同じ仕様を複数場所で独立管理しない。
- 正本の変更はGitHubの履歴で追跡できる状態にする。

## 3. 文書と実体の役割

### 3.1 正本

`docs/正本/`

目的、要件、設計、API、工程、テスト基準を定める。

### 3.2 実装指示書

`docs/実装指示書/`

各工程でClaude Codeが実装する内容を具体化する。正本を変更してはならない。

### 3.3 ChatGPT側現在地

`tasks/CHAT_CURRENT.md`

ChatGPTが確認した正本、現在地、判断、課題、未決事項、次指示、完了判定根拠を記録する。

### 3.4 Claude Code側現在地

`tasks/TASK_CURRENT.md`

Claude Codeが実装した内容、変更ファイル、テスト結果、残件、実装上の現在地を記録する。

### 3.5 実装コード

コードは実際に何が動いているかを示す実体であるが、仕様を独自に決める正本ではない。

## 4. 役割分担

### ChatGPT

ChatGPTは設計・管理・判断を担当する。

- 正本を読む
- 必要な旧資料・実機結果を確認し、設計知見として正本へ反映する
- 現在地を把握する
- 課題を特定する
- 既に確定した内容を守る
- 古い記載と本当の未決事項を分ける
- アプリの目的から優先順位を判断する
- 必要な修正方針を決める
- Claude Codeへ完全な実装指示を出す
- Claude Codeの報告を自分で検査する
- 次工程へ進めるか止めるか判定する
- `tasks/CHAT_CURRENT.md` を更新する

Claude Codeの報告を言い換えるだけで仕事を終えない。

### Claude Code

Claude Codeは実装担当である。

- 着手前に正本、実装指示書、CHAT_CURRENT、TASK_CURRENTを読む
- 新リポジトリ内の現行実装を調査してから変更する
- 指示された工程だけを実装する
- 静的検査、自動テスト等を実施する
- 実装結果を `tasks/TASK_CURRENT.md` に記録する
- 未確定事項を実装都合で勝手に確定しない
- 次工程へ自動で進まない

### ユーザー

ユーザーは目的・重要仕様の最終判断、実機確認、MVP完了確定、デプロイ実行の明示承認を行う。

### デプロイ

- Claude Codeは自動でデプロイしない。
- ChatGPTが正本・差分・テスト結果を検査してデプロイ可否を判定する。
- ユーザーが明示承認した後、Claude Codeが指定環境へデプロイする。
- 認証・権限上Claude Codeが実行できない場合だけ、ChatGPTがユーザーへ手動操作を依頼する。
- stagingで工程受入を行い、production反映はMVP完了判定後の別承認とする。

## 5. 調べてから答える

ChatGPTもClaude Codeも、資料やコードを「読め」と指定された場合は実際に開いて確認する。

確認できなかったものは「未確認」と明記する。

読んでいない資料を読んだ前提で判断しない。

推測で不足を埋めない。

## 6. Claude Code報告の扱い

Claude Codeの報告を受けた後、ChatGPTは次の順に処理する。

1. 現状把握
2. 正本・コード・テスト結果との照合
3. 課題の特定
4. 完了／修正／停止の判断
5. 必要な実行指示
6. 結果確認
7. 完了判定
8. CHAT_CURRENT更新

報告の要約や言い換えだけで次へ進まない。

## 7. 実装指示の形式

ユーザーが「指示」「Claude Codeへの指示」「実行指示」を求めた場合、ChatGPTは以下の2要素だけを返す。

1. 「どのアプリで」「どこを開いて」「何を貼って」「どうなれば完了か」を含む操作指示を1文で書く。
2. その直下に、そのままコピーして貼れる本文をコードブロックで出す。

## 8. 正本の作成順序

原則として次の順に確定する。

1. 案件概要書
2. 要件定義書
3. 統合設計書
4. API・内部関数一覧
5. 技術選定理由書
6. 開発工程表・テスト計画
7. 実装指示書

下位文書は上位文書を独自に変更しない。

## 9. 旧実装と新実装の扱い

旧「機械販売事例まとめアプリ」のコード、DB、API、画面、テストは、新アプリの実装基盤として再利用しない。

旧プロジェクトから引き継ぐのは、設計段階で文章化し正本へ反映した知見・失敗知見だけとする。

新規実装開始後は、新リポジトリ内の現行コードを実体として調査する。ただし、そのコードが正本と矛盾する場合は正本を優先する。

## 10. 変更と完了の原則

- 要約・説明文で正本本文を上書きしない。
- 説明用の短縮表現は、正本の詳細仕様を代替しない。
- 仕様判断時は要約ではなく元の正本文を確認する。
- 正本確定前の再クロスレビューは、関連する正本文そのものを全文対象として行う。

- 正本変更と実装変更を混同しない。
- 未確認事項を完了扱いしない。
- テスト未実施を合格扱いしない。
- 技術的に動くだけで販売事例品質を合格扱いしない。
- 次工程へ進む前に、当該工程の完了条件と残件を明示する。
- ユーザー承認が必要な判断は勝手に確定しない。

## 11. CHAT_CURRENTとTASK_CURRENT

両ファイルは互いに読める状態にするが、役割を混ぜない。

- ChatGPTは原則 `tasks/CHAT_CURRENT.md` を更新する。
- Claude Codeは原則 `tasks/TASK_CURRENT.md` を更新する。
- 相手側の記録を独自判断で書き換えない。
- 仕様変更は進捗ファイルではなく正本へ反映する。
- 進捗ファイルの記載が正本と矛盾する場合、正本を優先する。

## 12. 禁止事項

- 読んでいない資料を読んだことにする
- Claude Codeの報告をそのまま事実確定する
- 古い正本を新仕様の根拠にする
- 旧工程番号や旧関数名を理由なく継承する
- 実装都合で要件を削る
- AIの推測を確認済み事実として扱う
- 失敗をfallback追加だけで隠す
- 正本より進捗記録を優先する
- 次工程へ自動着手する
