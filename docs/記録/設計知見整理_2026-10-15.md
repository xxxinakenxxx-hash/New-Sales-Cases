# 新販売事例 設計知見整理

- 文書区分: 記録
- 作成日: 2026-10-15
- 目的: 実装前に、旧プロジェクト・旧Gem・旧ネタ帳・実機失敗から得た知見を文章化し、新正本へ反映済みかを確認する

## 1. 基本方針

本書は旧コードを再利用するための調査ではない。

旧プロジェクトから引き継ぐのは、設計段階で得た知見と失敗知見だけである。

それらを本書で文章化し、案件概要書・要件定義書・統合設計書・API一覧へ反映してから新規実装へ進む。

## 2. 引き継ぐ設計知見

### K-01 材料全体を先に理解する

入力項目、自由メモ、回答、添付資料を案件単位でまとめて理解する。

直前の1問1答だけを見て次質問を決める方式を中心設計にしない。

### K-02 既知情報を聞き直さない

入力済み、資料に明示済み、すでに回答済みの内容を原則として再質問しない。

### K-03 不足質問は原則1回のまとまり

質問を1問ずつ連鎖させない。

販売事例として価値の高い不足だけを原則1回のバッチで提示する。

不足がなければ0件を正常とする。

### K-04 2回目質問は例外

2回目以降の質問は、重大矛盾、新しい重要論点、利用者の明示要求がある場合だけ許可する。

### K-05 固定fallback質問で品質問題を隠さない

AI質問が重複除外された後に、固定質問を順番に出して帳尻を合わせる方式を禁止する。

質問が作れない場合は、原因を検出し、事実確認へ進めるか追加取材が必要かを正しく判断する。

### K-06 candidateとconfirmedを分離する

AI抽出結果はcandidateから開始する。

AIだけでconfirmedにしない。

人間が根拠を確認して初めてconfirmedとする。

### K-07 根拠追跡を必須とする

factは、どの入力・回答・資料を根拠にしたか追跡できること。

根拠のない数値、顧客発言、固有名詞、感情、効果を確定事実にしない。

### K-08 confirmed-only編纂

完成事例の確定本文はconfirmed factだけを根拠に生成する。

candidate / needs_check / rejectedを混ぜない。

### K-09 会話制御上の返答をfact化しない

「分かりません」「意味が分かりません」「はい」「そう書きました」等は販売事実ではない。

### K-10 candidate数を増やすことを前進とみなさない

同義・近似candidateの細分化を抑止する。

fact数・質問数だけで品質を評価しない。

### K-11 営業担当者の言葉と温度感を残す

AIは、営業担当者の言葉を不必要にコンサル用語へ置き換えない。

営業担当者本人が「自分の案件だ」と感じられることを重視する。

### K-12 因果関係のある販売事例にする

単なる項目一覧ではなく、課題→壁→突破→成果→喜びが読める内容にする。

営業担当者の判断、工夫、選定理由、比較検討、連携、横展開ポイントを残す。

### K-13 旧ネタ帳10領域は入力骨格であり固定質問票ではない

旧ネタ帳10領域を参考にするが、全項目必須にはしない。

domain空欄を埋めるために質問しない。

### K-14 数値・顧客発言は存在するものだけを使う

不明な数値や顧客発言をAIが補完・創作しない。

### K-15 構造化データを正本にする

完成HTMLやAI生成文を正本にしない。

source / fact / evidence / state / version / compilation / publicationを構造化して保持する。

### K-16 履歴とversionを失わない

fact修正、編纂、公開改訂は旧版を物理削除せず追跡可能にする。

複数端末の意図しない上書きをversion競合で防ぐ。

### K-17 技術的成功と販売事例品質を分ける

保存成功、API成功、自動テスト成功だけで完成としない。

実際の営業担当者と別営業担当者が、内容の正しさ・再利用性・質問負担を実機評価する。

### K-18 資料読取失敗を推測で補わない

読めない資料は未読として扱う。

1資料の失敗で正常sourceを壊さない。

### K-19 コメントは事実とは別に扱う

コメントは補足・質問・横展開アイデアの蓄積手段であり、confirmed factではない。

AIが自動で事実化・本文反映しない。

### K-20 公開済み事例は全社横断で再利用する

公開済み販売事例は、認証済み社内利用者が所属拠点・部門・上司部下関係に関係なく検索・閲覧できる。

manager専用の管轄閲覧はMVPに設けない。

## 3. 旧プロジェクトで繰り返さない失敗

- 逐次1問方式の長期化
- semantic重複除外後の固定fallback偏重
- 質問生成・coverage・fallback・終了判定の相互干渉
- 会話上の返答のcandidate化
- candidateの細分化・大量重複
- fact数・質問数を品質とみなすこと
- 技術テスト合格を販売事例品質の合格とみなすこと
- 実装都合で正本を曲げること
- 旧コードから仕様を逆輸入すること

## 5. 判定

現時点で把握している旧プロジェクト・旧Gem・旧ネタ帳・実機失敗からの設計知見は文章化し、新正本へ反映済みである。

今後、新しい知見が出た場合は、実装へ直接持ち込まず、先に本書または記録へ追加し、必要な正本を更新してから実装へ進む。
