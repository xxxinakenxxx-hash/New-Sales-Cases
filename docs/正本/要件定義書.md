## 1. 本書の目的

本書は「新販売事例」のMVPで実現する業務要件、機能要件、品質要件、データ・AI利用上の原則、受入条件を定義する。

旧「機械販売事例まとめアプリ」の既存コード、旧API、旧DB、旧工程番号を前提に要件を決めない。

旧Gem・旧ネタ帳、旧プロジェクトの実機結果は、要件を考えるための参考資料として扱う。

## 2. MVPの目的

営業担当者が持つ断片的な情報、記憶、ネタ帳、自由メモ、資料等から、AIが案件全体を理解し、不足情報だけを確認し、人間が確認した事実を根拠として、他の営業が実際の提案・教育・類似案件で再利用できる販売事例を作成・蓄積・検索できること。

MVPの中心成果物は「AIが文章を生成すること」ではなく、次の3点を同時に成立させることである。

1. 営業担当者の入力負担を抑えながら、販売事例として必要な情報を引き出せる
2. AIの推測ではなく、根拠と人間確認を持つ事実から完成事例を作れる
3. 完成事例を後から検索・再利用できる構造化営業資産として残せる

## 3. 対象利用者

MVPでは以下の利用者を想定する。

- 営業担当者
- 営業管理者
- 管理者
- システム管理者

詳細な権限マトリクスは統合設計書で確定する。

## 4. 利用端末

- 会社PC
- スマートフォン

営業担当者が外出先でも入力・確認できることを前提とする。

具体的な対応OS・ブラウザは画面設計で確定する。認証方式・ホスティング方式は `docs/正本/技術選定理由書.md` を正本とする。

## 5. MVPの業務フロー

MVPの基本フローは次のとおりとする。

1. 新規販売事例の作成を開始する
2. 営業担当者が分かる範囲の情報を入力する
3. 必要に応じて自由メモや資料を追加する
4. AIが入力材料全体を確認する
5. AIが既知情報、事実候補、不足情報を整理する
6. 販売事例として価値の高い不足だけを利用者へ確認する
7. 利用者が回答、不明、後で確認、省略を入力する
8. AIが回答をもとに事実候補を更新する
9. 利用者が事実候補を確認・修正・却下・要確認にする
10. 確認済み事実だけを根拠に販売事例を編纂する
11. 利用者が完成内容を確認する
12. 利用者が完成内容を確認した後、社内公開する
13. 公開事例を検索・閲覧・コメント・印刷・再利用する
14. 必要に応じて公開済み事例の改訂を開始し、事実確認・再編纂・再公開する

途中で中断しても再開できること。

## 6. 入力要件

### 6.1 基本方針

利用者に最初から完成文章を書かせない。

営業担当者は、自分が分かる範囲だけ入力して事例作成を開始できること。

未入力があること自体をエラーにしない。

AIが空欄を機械的に埋めるための固定質問票にはしない。

営業担当者が持っている断片的な情報、記憶、自由メモ、資料を、まず案件理解の材料として受け取る。

最初の入力段階で、利用者に分からない情報を無理に思い出させない。

### 6.2 初期入力で扱う情報領域

旧ネタ帳で有効だった次の10領域を最低限の設計参考とする。

1. お客様の基本情報
2. お客様は何に困っていたか
3. 導入前と導入後を数字でいうとどう変わったか
4. 何を提案したか
5. 他に検討したもの
6. 一番の壁
7. どう乗り越えたか
8. 誰に助けてもらったか
9. お客様が言ってくれた言葉
10. 自分が一番嬉しかったこと

これらは入力可能な情報領域であり、10項目すべてを必須入力にはしない。

旧ネタ帳の10領域を、そのまま固定質問票として順番に入力させる方式にはしない。

初期入力では、少なくとも次の種類の材料を扱えること。

- 顧客・案件に関する基本情報
- 自由メモ
- 商談経緯
- 現場で起きたこと
- 営業担当者の判断・工夫
- 会話
- 感情
- 背景
- 添付資料
- 上記10領域に相当する情報

### 6.3 自由入力

上記の項目に収まらない情報を自由メモとして入力できること。

自由メモには、商談経緯、現場での出来事、担当者の判断、会話、感情、背景等を含められること。

自由メモは、単なる補足欄ではなく、営業担当者が頭の中や手元に持っている断片情報を案件理解へ渡す正式な入力sourceとして扱う。

### 6.4 資料入力

資料添付はMVP必須とする。

営業担当者は、ネタ帳・自由メモだけでなく、案件理解に必要な資料を追加できること。

MVP対応形式:

- PDF
- JPG / JPEG
- PNG
- DOCX
- XLSX
- PPTX
- TXT
- CSV

上限:

- 1ファイル最大20MB
- 1案件あたり有効添付最大10ファイル
- 1案件あたり最大合計200MB

AIは、添付資料を単独で評価するのではなく、入力項目、自由メモ、既存回答等の他のsourceとあわせて案件単位で理解する。

物理保存方式とOCR・抽出方式の基本構成は `docs/正本/技術選定理由書.md` を正本とする。画像PDF、JPG/JPEG、PNGのOCRにはGoogle Cloud Document AI Enterprise Document OCRを使用する。

資料読取に失敗した場合は、その資料を未読として扱い、読めなかった内容をAIが推測で補わない。

OCR・抽出結果に判読不確実な箇所がある場合は、確定したsource本文として黙って扱わず、読取注意・要確認箇所として利用者に分かる状態を保持する。

不確実なOCR・抽出結果を、確実な根拠と同じ扱いでfact確認や編纂へ流さない。

## 7. AIによる案件理解要件

### 7.1 全材料をまとめて見る

AIは、入力項目、自由メモ、回答、利用可能な資料を案件単位でまとめて理解する。

質問ごとに局所的な直前文脈だけを見る逐次質問方式を前提としない。

AIは質問生成の前に案件全体を評価し、既知情報、既存fact、既回答、資料内容を踏まえて不足を判断する。

### 7.2 既知情報を再質問しない

入力済み、資料に明示済み、すでに回答済みの内容を原則として再質問しない。

既知情報を別表現で言い換えて再質問することも避ける。

### 7.3 不足の意味

「入力欄が空いていること」と「販売事例として本当に不足していること」を区別する。

不足判定は、少なくとも次の観点を考慮する。

- 課題が具体的に分かるか
- 提案内容が分かるか
- なぜその提案だったのかが分かるか
- 比較検討や選定理由が分かるか
- 壁と突破が分かるか
- 営業担当者の判断・工夫が分かるか
- 結果・変化が分かるか
- 顧客の言葉があるか
- 横展開に必要な情報があるか
- 因果関係が破綻していないか

未入力domainが残っていることだけを、不足質問の発生条件にしない。

### 7.4 追加質問方式

追加質問は、固定質問の順番消化にしない。

販売事例として価値の高い不足だけを選ぶ。

質問が不要なら0件を正常とする。

必要な質問は、利用者負担を抑えるため、原則として1回分のまとまりで提示する。

質問数に固定上限を先に置き、重要情報を切り捨てる方式にはしない。

ただし、極端に多い質問をそのまま表示しない。

表示前にAI側で少なくとも次を除外する。

- 既知情報
- 回答済み情報
- 同義・重複質問
- 空欄を埋めるだけの低価値質問
- 推測を誘導する質問
- 回答不能な抽象質問

回答送信後に、自動的に次の質問バッチを生成する方式にはしない。

### 7.5 2回目以降の質問

2回目以降の自動質問は通常フローでは発生させない。

次のいずれかの場合だけ許容する。

1. 1回目の回答によって重大な矛盾が新たに生じた
2. 1回目の回答によって新しい重要論点が判明し、それがないと事例の因果関係が成立しない
3. 利用者が明示的に追加取材を実行した

単に未入力domainが残っていることを理由に2回目の質問を出さない。

### 7.6 質問品質

質問は具体的であること。

悪い例:

- 「詳しく教えてください」
- 「ほかにありますか」

良い例:

- 「導入前の包餡作業は1日何時間かかっていましたか？」
- 「A社製ではなく今回の機械を選んだ決め手は何でしたか？」

分からない情報を無理に思い出させない。

## 8. 回答状態要件

各質問に対して、通常回答だけでなく以下の状態を持てること。

- 回答済み
- 分からない
- 後で確認
- 今回は省略

空欄と明示的不明を区別する。

「後で確認」は未回答の保留状態として残し、事実確認へ進んだ後でも再表示して回答できること。

後から回答した内容はsourceへ追加し、関連candidateを再評価する。

保留質問が残っていることだけを理由に編纂を禁止しない。編纂可能性はconfirmed factの内容で判断する。

「分からない」「意味が分からない」「はい」「そう書きました」「後で確認します」等の会話制御上の返答を、そのまま販売事実として扱わない。

## 9. 事実候補要件

### 9.1 AI生成内容の位置づけ

AIが抽出した事実は、最初はcandidateであり、確認済み事実ではない。

AIだけでconfirmedにしない。

confirmedへ変更できるのは、少なくとも次を満たす場合とする。

- 根拠sourceが存在する
- 対象caseが一致する
- 利用者が確認した
- AI推論だけではない

### 9.2 事実候補の根拠

事実候補は、どの入力・回答・資料を根拠にしたか追跡できること。

factごとに根拠抜粋を保持できること。

根拠のない数値、固有名詞、顧客発言、感情、効果を作らない。

OCR・抽出等で不確実なsourceを、確実な根拠と同じ扱いでconfirmed化しない。

### 9.3 状態

最低限、以下の状態を扱う。

- candidate
- confirmed
- rejected
- needs_check
- superseded

### 9.4 修正と履歴

candidateを修正してconfirmedにする場合、元candidateを消さず、変更前の内容を追跡できること。

confirmed factを後から修正する場合も、新版を作り、旧版をsupersededとして保持する。

物理削除だけで履歴を失わない。

### 9.5 重複・細分化・衝突抑制

同じ意味のcandidateを大量に作らない。

会話の1文を機械的に複数factへ細切れにしない。

少なくとも次を確認する。

1. 完全一致
2. 数値・固有名詞を除いた意味近似
3. 同domain内の意味重複
4. 既存confirmedとの衝突

AI判定だけで既存factを破棄しない。

必要に応じて利用者へ統合候補を提示する。

構造化は検索と根拠追跡を助けるために行い、販売事例の因果関係を壊さない。

## 10. 事実確認要件

利用者はcandidateとその根拠を確認できること。

事実確認では少なくとも次を確認できること。

- 事実領域
- candidate本文
- 根拠抜粋
- 根拠元
- 現在状態
- 矛盾
- 類似candidate

利用者は少なくとも以下を行えること。

- そのまま確認
- 内容を修正して確認
- 却下
- 要確認
- 必要な事実を手動追加
- 根拠を見る

修正・追加した場合も、誰が何を根拠に変更したかを追跡できる設計とする。

手動追加したfactも、追加直後から自動confirmedにはせず、根拠を持つcandidateとして追加し、確認操作を経てconfirmedにする。

confirmed factだけを原則として編纂根拠に使用する。

candidate、needs_check、rejected、根拠不明の情報を、確定事実として本文へ混入させない。

未confirmed factや保留質問が残っていても、confirmed factだけで販売事例として成立する場合は編纂可能性を評価する。

confirmed factだけでは販売事例として成立しない場合は、何が不足しているかを利用者に明示する。

## 11. 編纂要件

### 11.1 根拠

完成事例は原則としてconfirmedの事実だけを根拠に生成する。

needs_check、rejected、根拠不明の情報を、確定事実として本文へ混入させない。

### 11.2 品質

完成事例は、単なる項目列挙や短いAI要約にしない。

最低限、読み手が次を理解できること。

- 顧客・現場の背景
- 課題
- 提案内容
- 提案・選定理由
- 比較検討
- 一番の壁
- 突破方法
- 営業担当者の判断・工夫
- 社内外の連携
- 導入前後の変化
- 顧客の言葉
- 担当者の手応え・喜び
- 成功要因
- 注意点
- 刺さる顧客像
- 横展開ポイント
- 一連のストーリー

### 11.3 ストーリー

事例のストーリーは、案件に事実が存在する範囲で、

課題との出会い → 壁 → 突破 → 成果 → 喜び

の因果が読めることを重視する。

営業担当者の言葉を不必要にコンサル用語へ置き換えない。

担当者が読んで「そうそう、こういうことだった」と認識できる内容を目標とする。

### 11.4 顧客の言葉

顧客発言は、根拠があるものだけを引用・要約する。

存在しない顧客発言をAIが創作しない。

引用として表示する場合は、原文性が確認できること。

### 11.5 数値

導入前後、投資額、効果、売上等の数値は、根拠がある場合だけ使う。

AIが推定値を確定数値として作らない。

## 12. 編纂確認・版管理

完成事例は利用者が確認できること。

表現修正と新事実追加を区別する。

新事実が必要な修正は、事実確認工程へ戻せること。

再編纂した場合、過去版を追跡できること。

どの編纂版が確認完了・公開されているか分かること。

## 13. 公開・承認

MVPでは承認フローを実運用しない。

営業担当者が完成内容を確認した後、そのまま社内公開できることを基本とする。

ただし、将来の承認運用に備えて、承認状態・承認者・承認日時等を持てる拡張余地は設計上確保する。

現時点では承認画面・承認操作を通常フローに出さず、機能として使用しない。

公開後は公開停止できること。

公開済み事例を更新する場合、現在公開中の版を直ちに消さず、改訂作業を別状態で開始できること。新しい編纂版を確認後に再公開し、公開版を差し替える。

### 13.1 MVPの標準公開範囲

MVPは社内利用を対象とする。

社内公開済み販売事例は、認証済みの社内利用者が所属拠点・部門に関係なく全社横断で検索・閲覧できることを基本とする。

確認済みの顧客名・金額は、MVPでは社内利用者に通常表示する。MVPでは一般利用者向けの表示切替UIは設けず、公開時は表示を標準とする。

社外公開はMVPでは行わない。

匿名共有版はMVP対象外とする。

## 14. 検索要件

### 14.1 基本

完成事例を後から探せること。

キーワード検索だけでなく、構造化された情報を条件として利用できること。

### 14.2 検索対象候補

- 顧客業種・業態
- 顧客課題
- 対象工程
- 機械分類・機械名
- メーカー
- 提案内容
- 採用理由
- 導入効果
- 壁と突破
- 成功要因
- 注意点
- 刺さる顧客像
- 横展開ポイント
- 拠点
- 登録時期
- 検索用全文

最終的なフィルタ項目は統合設計で確定する。

### 14.3 検索結果

一覧で、少なくとも「なぜこの事例を見る価値があるか」が分かること。

単に顧客名と機械名だけを並べる一覧にしない。

## 15. 詳細表示要件

販売事例の詳細画面で、完成ストーリーと主要な構造化情報を確認できること。

必要に応じて、根拠・確認状態・履歴を見る管理用導線を分離する。

営業利用画面に内部管理情報を過剰表示しない。

## 15.1 コメント要件

コメント機能はMVPに含める。

対象は公開済み販売事例とする。

認証済み社内利用者は、公開済み販売事例にコメントを投稿できること。

コメントの主な用途は以下とする。

- 事例への補足
- 他案件への横展開アイデア
- 質問
- 利用時の注意点
- 作成者へのフィードバック

コメントは販売事例のconfirmed factではない。

コメント内容をAIが自動で事実化したり、公開本文へ自動反映したりしない。

コメントを販売事例へ反映したい場合は、作成者が改訂を開始し、通常のfact確認フローを通す。

コメント本文は、MVPの販売事例検索索引およびA4/PDF出力には含めない。

利用者は自分のコメントを編集・削除できること。

admin / sysadminは不適切なコメントを削除できること。

コメントには投稿者、投稿日時、更新日時を保持すること。

コメントはcase単位で保持し、コメント投稿時点のpublication版も追跡できること。

公開済み事例を改訂して再公開しても、既存コメントは保持する。

公開停止中は通常利用者向けのコメント表示・新規投稿を停止するが、コメントデータ自体は削除しない。再公開後は既存コメントを再表示できること。

## 16. 印刷・PDF要件

販売事例を営業活動で利用できるA4印刷・PDF出力はMVP必須とする。

旧Gemで有効だった情報要素は参考にするが、旧HTMLテンプレートや旧表裏構成をそのまま正本にはしない。

出力は正本データから再生成可能であること。

MVPでは社内利用版を対象とする。匿名共有版はMVP対象外とする。

MVPでは **A4縦1ページ、1事例1ページ** のA4印刷・PDF出力を必須とする。画面をそのまま印刷せず、営業利用向けの専用レイアウトを使用する。複数事例の一括出力はMVP対象外とする。

## 17. 中断・再開

以下の途中状態を失わず再開できること。

- 初期入力途中
- AI不足確認前
- 質問回答途中
- 事実確認途中
- 編纂確認途中

ブラウザ更新、端末変更等を考慮し、サーバー側に必要な状態を保存する。

## 18. 競合・履歴

複数端末・複数操作による意図しない上書きを防ぐこと。

事実、編纂、公開等の重要変更は、少なくとも更新競合を検出できること。将来承認を有効化する場合は、承認操作も同様に競合検出対象とする。

具体方式は統合設計で確定する。

## 19. 権限・セキュリティ

- 利用者権限をクライアント表示だけで制御しない
- サーバー側でも認可する
- APIキー、アクセストークン等を画面やログに出さない
- 権限外の下書き・非公開事例を検索結果へ出さない
- 個人情報・顧客機密の扱いを考慮する
- AIへ送信する情報範囲を設計上明示する
- ログへ不要な全文データを残さない

認証方式は `docs/正本/技術選定理由書.md`、権限体系は統合設計書を正本とする。秘密情報管理の具体方式は両正本に従って物理設計へ落とし込む。

## 20. ログ・分析

MVPでは、運用改善に必要な最低限の行動ログを記録できることを必須とする。

ランキング機能はMVP対象外とする。

候補:

- 事例作成開始
- 初期入力保存
- AI不足確認実行
- 質問表示
- 回答
- 事実確認
- 編纂
- 公開
- 検索
- 事例閲覧
- コメント投稿
- コメント編集
- コメント削除
- 途中離脱（一定期間進行がない案件として集計）
- 再開

質問数やcandidate数だけを品質指標にしない。

品質評価では、完成事例の実用性、入力負担、再利用性を重視する。

## 21. エラー・障害時要件

AI処理、通信、保存、資料読取等に失敗しても、入力済み情報を可能な限り失わない。

利用者に、何が失敗したか、何が保存済みか、次に何をすればよいか分かる表示をする。

内部エラーや秘密値をそのまま画面へ出さない。

## 22. データ原則

### 22.1 正本データ

完成HTMLやAI生成文ではなく、確認済み事実・根拠・状態・版情報を正本データとして扱う。

### 22.2 表示成果物

カード、詳細画面、印刷、PDF等は正本データから再生成可能な成果物とする。

### 22.3 AI推論

AIによる推論や補完を、確認済み事実と同じ領域へ自動保存しない。

推論を表示する場合は、事実と明確に区別する。

## 23. 既存データ・旧コード

旧プロジェクトのコード、DB、API、画面、テストは新アプリの実装基盤として再利用しない。

本MVPは新正本を基準に新規実装する。

旧プロジェクトから引き継ぐのは、設計段階で文章化し正本へ反映した知見・失敗知見だけとする。

旧データはMVP開始時に自動移行しない。将来、移行が必要になった場合は別途移行要件・テストを定義する。

### 23.1 旧データ移行

旧データのMVP初期移行は行わない。

まず新システムを完成させ、実機品質を確認した後に、旧データを移行するかどうかを別途判断する。

## 24. 技術選定とMVP対象外

### 24.1 技術構成

技術構成は `docs/正本/技術選定理由書.md` を正本とする。

基本構成:

- TypeScript / Next.js
- Google Cloud Run
- PostgreSQL / Google Cloud SQL
- Google Cloud Storage
- Google Workspace OIDC
- PostgreSQL構造化検索 + 全文検索
- AI provider adapter
- ファイル形式別parser + OCR
- 印刷専用HTML/CSS + headless Chromium PDF
- PostgreSQL業務監査ログ + Cloud Logging技術ログ

AI providerはOpenAI API、OCRはGoogle Cloud Document AI Enterprise Document OCR、検索基盤はCloud SQL for PostgreSQL 18 + pg_bigm、添付上限とA4/PDFレイアウトは技術選定理由書・統合設計書の確定内容に従う。

### 24.2 MVP対象外

以下はMVPへ含めない。

- ベクトル検索
- 自動通知
- 外部システム連携
- 高度なレコメンド
- 自動スライド生成
- 動画生成

- 匿名共有版
- 人気ランキング・営業担当ランキング等のランキング機能

- 複数事例の一括PDF出力

後続で必要性が確認された場合は、正本を改訂して追加する。

## 25. MVP受入条件

MVP完了候補とするため、少なくとも以下を満たすこと。

### 25.1 入力・AI取材

- 分かる範囲だけで事例作成を開始できる
- 既知情報を不必要に再質問しない
- 固定質問の順番消化にならない
- 不足質問0件を正常に扱える
- 不足質問が必要な場合、営業価値の高い内容に絞られている
- 利用者が「分からない」「後で確認」「省略」を選べる
- 途中で中断・再開できる

### 25.2 事実管理

- AI抽出はcandidateから始まる
- candidateが自動confirmedにならない
- 根拠を追跡できる
- 修正前の内容を追跡できる
- rejected / needs_checkを完成事例の確定根拠にしない
- 会話上の返答を販売事実へ誤変換しない
- 同義candidateの大量発生を抑止できる

### 25.3 編纂品質

- confirmedだけを根拠に完成事例を作る
- 架空の数値・顧客発言・感情を作らない
- 課題、提案、壁、突破、成果の因果が読める
- 営業担当者の判断・工夫が分かる
- 営業担当者の言葉・温度感が残る
- 他の営業が「自分の顧客にも使えそう」と判断できる情報がある

### 25.4 検索・再利用

- 完成事例を検索できる
- 構造化条件を利用できる
- 一覧から事例の価値が分かる
- 詳細を確認できる
- 検索結果から営業再利用に必要な情報へ到達できる

### 25.5 コメント

- 公開済み事例の詳細からコメント一覧を確認できる
- 認証済み社内利用者がコメントを投稿できる
- 自分のコメントを編集・削除できる
- 他人のコメントを一般利用者が編集・削除できない
- admin / sysadmin が管理上必要なコメントを削除できる
- コメントをAIが自動でfact化・本文反映しない
- 事例改訂後もコメントを保持できる
- 公開停止中は通常利用者へのコメント表示・新規投稿を停止し、再公開後に復元できる

### 25.6 運用

- 権限外操作を拒否できる
- 意図しない上書きを検出できる
- 重要変更の履歴を追跡できる
- AI・保存失敗時に入力を失わず復旧できる
- 秘密値を画面・ログへ出さない

## 26. MVP品質評価の考え方

MVP判定では、技術テストだけでなく実際の販売事例品質を評価する。

実機評価では少なくとも次を確認する。

1. 営業担当者にとって入力・回答負担が許容できるか
2. 不要な再質問がないか
3. 完成事例が事実に基づいているか
4. 営業担当者本人が内容に納得できるか
5. 別の営業担当者が内容を理解し、類似顧客へ使えると思えるか
6. 検索で必要な事例へ到達できるか

質問数、fact数、AI呼出回数だけで合格・不合格を決めない。
