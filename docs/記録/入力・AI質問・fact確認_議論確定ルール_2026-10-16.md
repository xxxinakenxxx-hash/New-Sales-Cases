# 新販売事例 入力・AI質問・fact確認 議論確定ルール

- 文書区分: 記録
- 作成日: 2026-10-16
- 目的: 初期入力、AI不足質問、fact確認について、これまでの議論で確定したルールを要約で潰さず、実装・再クロスレビュー時に参照できる形で明文化する。
- 注意: 本書は正本を置き換えない。正本の詳細ルールを短縮・再要約するための文書ではない。再クロスレビュー時は本書と正本文を突き合わせ、差分があれば正本側を修正する。

## 1. 初期入力の確定ルール

### 1.1 基本思想
- 利用者に最初から完成文章を書かせない。
- 営業担当者は「分かる範囲だけ」入力して開始できる。
- 未入力があること自体をエラーにしない。
- 空欄を埋めるためだけの固定質問票にはしない。
- 旧ネタ帳の10領域は設計上の参考とするが、10項目をそのまま必須入力票にはしない。
- 営業担当者が持っている断片的な情報、記憶、自由メモ、資料をまず材料として受け取る。
- 最初の入力段階で、営業担当者に無理に思い出させない。

### 1.2 入力材料
初期入力では、少なくとも次の種類の材料を扱えるようにする。

- 顧客・案件に関する基本情報
- 自由メモ
- 商談経緯
- 現場で起きたこと
- 営業担当者の判断・工夫
- 会話
- 感情
- 背景
- 添付資料
- 旧ネタ帳で有効だった10領域に相当する情報

旧ネタ帳で有効だった10領域は以下。

1. お客様の基本情報
2. お客様は何に困っていたか
3. 導入前と導入後を数字でいうとどう変わったか
4. 何を提案したか
5. 他に検討したもの
6. 一番の壁
7. どう乗り越えたか
8. 誰に助けてもらったか
9. お客様が言ってくれた言葉
10. 自分が一番嬉しかったこと

これらは入力可能な情報領域であり、全項目を必須入力にはしない。

### 1.3 資料添付
- 資料添付はMVP必須。
- PDF、画像、文書、表計算、テキスト等の案件資料を追加できるようにする。
- AIは添付資料だけを個別に見るのではなく、入力項目・自由メモ・回答等と合わせて案件単位で理解する。
- 読取に失敗した資料は「読めたこと」にしない。
- 読めなかった内容をAIが推測で補わない。
- OCR・抽出結果に判読不確実な箇所がある場合は、通常の確定sourceとして黙って扱わず、読取注意・要確認箇所として保持する。

## 2. AI不足質問の確定ルール

### 2.1 AIは案件全体を先に理解する
- AIは、入力項目、自由メモ、添付資料、既存回答を案件単位でまとめて確認する。
- 直前の1回答だけを見て次の質問を作る逐次質問方式を前提にしない。
- 既知情報を再質問しない。
- 入力済み、資料に明示済み、既回答の内容を原則として質問しない。

### 2.2 不足の判定基準
「入力欄が空いている」ことと「販売事例として本当に不足している」ことを分ける。

不足判定では少なくとも次を確認する。

- 課題が具体的に分かるか
- 提案内容が分かるか
- なぜその提案だったのかが分かるか
- 比較検討や選定理由が分かるか
- 壁と突破が分かるか
- 営業担当者の判断・工夫が分かるか
- 結果・変化が分かるか
- 顧客の言葉があるか
- 横展開に必要な情報があるか
- 因果関係が破綻していないか

### 2.3 質問方式
- 固定質問の順番消化にしない。
- 販売事例として価値の高い不足だけを質問する。
- 質問が不要なら0件を正常扱いする。
- 必要な質問は原則として1回分のまとまりで提示する。
- 固定件数上限を先に置いて重要情報を切り捨てない。
- ただし、極端に多い質問をそのまま表示しない。
- AI側で既知情報、重複質問、低価値質問、空欄を埋めるだけの質問、推測を誘導する質問、回答不能な抽象質問を除外する。
- 「詳しく教えてください」「ほかにありますか」のような抽象質問を避ける。
- 具体的に答えられる質問にする。
- 分からない情報を無理に思い出させない。

### 2.4 2回目以降の質問
通常フローでは、回答送信後に自動で次の質問バッチを生成しない。

2回目以降を許すのは次の場合だけ。

1. 1回目回答によって重大な矛盾が新たに生じた
2. 1回目回答によって新しい重要論点が判明し、それがないと事例因果が成立しない
3. 利用者が明示的に「追加取材」を実行した

単に未入力domainが残っていることを理由に2回目を出さない。

### 2.5 回答状態
各質問は次の状態を持てる。

- 回答済み
- 分からない
- 後で確認
- 今回は省略

追加ルール:

- 空欄と「分からない」を区別する。
- 「後で確認」は保留質問として残す。
- fact確認へ進んだ後でも保留質問へ戻って回答できる。
- 後日回答した内容はsourceへ追加し、関連candidateを再評価する。
- 保留質問が残っていることだけを理由に編纂禁止にしない。
- 「分かりません」「意味が分かりません」「はい」「そう書きました」「後で確認します」等の会話制御返答を販売事実として扱わない。

## 3. fact確認の確定ルール

### 3.1 AI抽出は必ずcandidateから開始
- AIが抽出した事実は最初からconfirmedにしない。
- AIだけの判断でconfirmedにしない。
- candidate、confirmed、rejected、needs_check、supersededを扱う。
- confirmedにできるのは、根拠sourceがあり、対象caseが一致し、利用者が確認し、AI推論だけではない場合。

### 3.2 根拠追跡
- 各factは、どの入力、回答、資料を根拠にしたか追跡できる。
- 根拠抜粋を保持する。
- 根拠のない数値、固有名詞、顧客発言、感情、効果を作らない。
- OCR等で不確実なsourceを、確実な根拠として扱わない。

### 3.3 fact確認画面で必要な情報
少なくとも次を確認できるようにする。

- 事実領域
- candidate本文
- 根拠抜粋
- 根拠元
- 現在状態
- 矛盾
- 類似candidate

### 3.4 利用者操作
利用者は少なくとも次を行える。

- 確認
- 修正して確認
- 却下
- 要確認
- 手動追加
- 根拠を見る

### 3.5 修正・履歴
- candidateを修正してconfirmedにする場合、元candidateを消さない。
- 元candidateは履歴追跡可能にする。
- confirmed factを後から修正する場合も新版を作り、旧版をsupersededとする。
- 物理削除だけで履歴を失わない。

### 3.6 重複・衝突
- 同義candidateを大量に作らない。
- 会話の1文を機械的に多数のfactへ細切れにしない。
- 完全一致、意味近似、同domain内の重複、既存confirmedとの衝突を確認する。
- AI判断だけで既存factを破棄しない。
- 必要に応じて利用者へ統合候補を提示する。

### 3.7 編纂へ使えるfact
- 原則としてconfirmed factだけを編纂入力に使う。
- candidate、needs_check、rejected、根拠不明情報を確定本文の根拠に混ぜない。
- 未confirmed情報が残っていても、confirmed factだけで事例として成立する場合は編纂可能性を評価する。
- confirmed factだけで販売事例が成立しない場合は、不足内容を明示する。

## 4. 今後UI設計で決める範囲

上記の業務ルールは再度ユーザーへ問い直さない。

UI設計で未確定なのは、上記ルールを満たすための具体的な見せ方・配置・操作密度だけとする。

- 初期入力欄の配置
- 自由メモと資料添付の配置
- 質問バッチの画面上の並べ方
- 回答状態の選択UI
- fact候補と根拠の並べ方
- conflict / duplicate / needs_checkの見せ方
- PC / スマートフォンでの配置
- 1画面内の情報密度
- 保存・次へ・戻る等の操作導線

これらのUI詳細を決める際も、本書および正本で確定した業務ルールを削らない、短縮しない、別ルールへ置き換えない。
