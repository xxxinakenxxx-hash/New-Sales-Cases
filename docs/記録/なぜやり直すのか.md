# なぜやり直すのか

更新日: 2026-10-14

## 1. この記録の目的

本書は、旧「機械販売事例まとめアプリ」を継ぎ足して修正するのではなく、新プロジェクト「新販売事例」として正本からやり直すことにした理由を残すための記録である。

今後、実装が進んだ際に「なぜ既存方式へ戻さないのか」「何を残し、何を捨てるのか」が曖昧にならないよう、判断の根拠を固定する。

## 2. 旧プロジェクトで目指していたこと

旧プロジェクトでは、営業担当者の短いメモを起点にAIが内容を整理し、販売事例として蓄積・検索・表示する仕組みを作ろうとしていた。

途中から、単なる要約では販売事例として弱いことが明確になり、AIによる追加質問、候補事実の抽出、利用者による事実確認、確認済み事実だけを使った編纂へ設計を拡張した。

この過程で、次の技術的な基盤は得られた。

- candidate と confirmed の分離
- rejected / needs_check 等の事実状態管理
- 根拠IDと fact_id の追跡
- confirmed のみを使う編纂
- 版管理と履歴保持
- expectedVersion 等による競合検出
- 構造化データを検索へ使う考え方
- 一覧、詳細、検索、ログ等の基礎

これらは失敗ではなく、新プロジェクトの設計知見として文章化し、正本へ反映する内容である。旧コードを再利用するという意味ではない。

## 3. 旧プロジェクトで起きた問題

問題は、機能が動くかどうかではなく、販売事例を作る中心部分の品質と設計にあった。

### 3.1 AI取材が長期化した

逐次的に1問ずつ質問する方式では、案件によって質問数が増え、利用者の負担が大きくなった。

また、既に回答済みの内容に近い質問や、営業価値の低い確認が混ざるようになり、「必要なことだけを聞く」という本来の目的から外れた。

### 3.2 重複除外とfallbackが取材品質を壊した

CASE-0000025の実機確認では、AIが生成した質問がsemantic重複判定で除外された後、固定的なfallback質問へ偏り、最終的に `AI_QUESTION_DECISION_INVALID` に至った。

これは単一不具合ではなく、質問生成、重複判定、coverage、fallback、終了判定が互いに干渉する構造上の問題だった。

### 3.3 会話上の返答まで事実候補になった

「はい。そう書きました」「意味が分かりません」「分かりません」といった会話上の反応までcandidate化するなど、販売事例に必要な事実と、会話制御上の発言を十分に分離できていなかった。

### 3.4 事実が細切れになり、因果関係が弱くなった

candidateを増やすこと自体が前進指標になり、同義・近似した事実が細分化される場面があった。

その結果、課題、提案理由、壁、突破、成果という販売事例として重要な因果関係よりも、事実の件数や分類の方が強くなった。

### 3.5 技術的合格と販売事例品質が乖離した

保存、状態管理、履歴、テストが通っていても、完成した内容が「営業が読みたい・使いたい販売事例」になっていないことがあった。

アプリの目的は技術的な一連動作ではなく、再利用できる営業資産を作ることなので、この乖離は許容できない。

## 4. 旧Gem・旧ネタ帳から再確認したこと

旧Gemと旧ネタ帳には、現在の実装より優れていた部分があった。

特に重要なのは次の点である。

- 入力された材料全体を先に読む
- 既に書かれていることは聞き直さない
- 足りない情報だけを質問する
- 質問を何度も小分けにせず、1回にまとめる
- 分からない項目は無理に埋めない
- 営業担当者の言葉と温度感を残す
- 「課題との出会い → 壁 → 突破 → 成果 → 喜び」をストーリーとしてつなぐ
- 顧客の言葉を勝手に作らない
- 「自分が一番嬉しかったこと」を事例の核として扱う

旧ネタ帳には以下の10項目があった。

1. お客様の基本情報
2. お客様は何に困っていたか
3. 導入前と導入後を数字でいうとどう変わったか
4. 何を提案したか
5. 他に検討したもの
6. 一番の壁
7. どう乗り越えたか
8. 誰に助けてもらったか
9. お客様が言ってくれた言葉
10. 自分が一番嬉しかったこと

旧Gemの弱点は、完成した文章やHTMLを作ることに強い一方、構造化保存、横断検索、根拠追跡、履歴管理、再編集の基盤が弱かったことである。

## 5. やり直しの判断

結論として、旧プロジェクトをそのまま工程追加で修正し続ける方式を終了する。

理由は、正本、工程表、API設計、実装の間に旧方式と新方式が混在し、どれを守るべきかが分かりにくくなったためである。

部分修正を続けると、新しい取材思想を旧アーキテクチャへ無理に押し込むことになる。

そのため、新プロジェクト「新販売事例」では以下の順でやり直す。

1. 案件概要書
2. 要件定義書
3. 統合設計書
4. API・内部関数一覧
5. 設計知見の文章化・正本反映確認
6. 技術選定理由書
7. 開発工程表・テスト計画
8. 残る設計事項の確定
9. 実装指示書
10. 新規実装

既存実装から逆算して新正本を作らない。

## 6. 新プロジェクトで残すもの

旧プロジェクトから残すのはコード資産ではなく、設計知見と失敗知見である。

- candidate / confirmed 等の事実状態管理
- 根拠追跡
- confirmed-only編纂
- 版管理、履歴管理、競合制御
- 構造化検索の考え方
- 既存の失敗ケースとテスト結果
- 旧Gemと旧ネタ帳の取材・ストーリー品質に関する知見

これらは `docs/記録/設計知見整理_2026-10-15.md` に文章化し、正本へ反映する。

旧GAS、旧スプレッドシート、旧DB、旧API、旧画面、旧テストを新アプリの実装基盤として再利用しない。

## 7. 新プロジェクトで戻さないもの

次は、そのまま完成形として復活させない。

- 1問ずつ延々と続くことを前提にしたAI取材
- 固定質問の順番消化
- fallback質問を増やすことで品質問題を隠す実装
- candidate件数や質問数を品質そのものとみなす考え方
- AI要約文を事実の正本にする方式
- HTMLを正本にする方式
- 技術テスト通過だけでMVP完了とする判定
- 旧工程番号、旧API、旧DB構造を先に固定すること

## 8. 新プロジェクトの中心思想

新販売事例は、旧Gemの「良い事例を引き出す力」と、旧アプリで得た「構造化・根拠・履歴・検索」の強みを統合する。

営業担当者が持つネタ帳、メモ、資料、会話記録等を材料としてAIが全体を理解し、既知情報と不足情報を分け、必要なことだけを確認し、人間が確認した事実を根拠に、他の営業が実際に再利用できる販売事例を作る。

この目的より、既存コードの都合、画面の都合、質問数、fact数、工程消化を優先しない。

## 9. この記録の扱い

本書は「なぜやり直したか」を残す判断記録であり、機能要件そのものの正本ではない。

仕様は `docs/正本/` 配下の文書で定義する。
