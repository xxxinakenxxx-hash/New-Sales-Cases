## 1. 本書の目的

本書は「新販売事例」の要件を、実装可能なシステム構造へ落とし込むための統合設計を定義する。

本書で定義する対象は以下とする。

- 全体アーキテクチャ
- 画面構成
- 状態遷移
- 入力構造
- AI処理
- 事実管理
- 編纂
- 公開・検索
- データ構造
- 権限
- エラー・競合・履歴
- ログ
- API境界

本書は業務論理・状態・データ・権限・API境界を定義する。物理技術構成は `docs/正本/技術選定理由書.md` を正本とする。

旧「機械販売事例まとめアプリ」のGAS、Googleスプレッドシート、旧関数名、旧DB列、旧工程番号は設計根拠にしない。

## 2. 設計原則

### 2.1 正本データと表示成果物を分ける

正本データは、入力元、回答、事実候補、確認済み事実、根拠、状態、版情報とする。

以下は正本データそのものではない。

- AIが生成した完成文章
- HTML
- カード表示
- PDF
- 印刷レイアウト
- 検索一覧

これらは正本データから生成される成果物とする。

### 2.2 AIは確定者ではない

AIの責務は以下に限定する。

- 入力材料の理解
- 事実候補抽出
- 不足情報判定
- 質問生成
- 回答の事実候補化
- confirmed事実からの編纂
- 検索用補助情報の生成

AIは自分の判断だけで事実をconfirmedにしない。

### 2.3 質問数ではなく販売価値を優先する

質問生成では、空欄数や質問件数を進捗指標にしない。

優先するのは、販売事例として意味のある因果関係を完成させることとする。

### 2.4 旧ネタ帳を固定質問票にはしない

旧ネタ帳10領域は、AIが案件を理解するための標準入力骨格として使う。

ただし、全項目入力を必須にしない。

空欄があること自体を不足とはみなさない。

### 2.5 実装より上位正本を優先する

実装中に既存コードや技術制約と衝突した場合、コード都合で正本を変更しない。

必要な変更はChatGPT側で正本へ反映してから実装指示を更新する。

## 3. 全体システム構造

システムは論理的に次の7領域へ分ける。

1. 入力領域
2. AI案件理解領域
3. 不足確認領域
4. 事実確認領域
5. 編纂領域（承認は将来拡張）
6. 公開・検索・閲覧・コメント領域
7. 管理・監査領域

処理の基本線は次のとおり。

```text
入力
  ↓
入力ソース保存
  ↓
AI案件理解
  ├─ 既知情報整理
  ├─ candidate fact生成
  └─ 不足情報評価
  ↓
不足質問バッチ
  ↓
回答
  ↓
candidate fact更新
  ↓
人間による事実確認
  ↓
confirmed facts
  ↓
AI編纂
  ↓
編纂レビュー
  ↓
公開
  ↓
検索・閲覧・コメント・印刷
```

## 4. 画面構成

MVPでは、営業担当者の操作負荷を減らすため、画面を業務目的単位で分ける。

### S-01 ホーム・案件一覧

目的:

- 新しい販売事例を作る
- 作成途中案件へ戻る
- 自分が関係する案件の状態を見る
- 公開済み事例を検索する

主要表示:

- 新規作成
- 作成途中
- 要確認
- 編纂確認待ち
- 公開済み
- 検索導線

管理者向け内部状態を営業画面へ過剰表示しない。

### S-02 事例入力

目的:

営業担当者が、最初から完成文章を書くことなく、自分が分かる範囲の情報・記憶・自由メモ・資料を一度に材料として渡せるようにする。

基本ルール:

- 未入力があること自体をエラーにしない
- 分からない情報を最初から無理に思い出させない
- 旧ネタ帳の情報領域を設計参考にするが、固定質問票にはしない
- 自由メモと資料も正式なsourceとして扱う
- 初期入力の空欄数を、そのままAI質問数へ変換しない

構成:

#### A. お客様・案件基本情報

- 企業名
- 所在地
- 業態
- 年商
- 従業員構成
- 営業担当
- 拠点
- 案件時期

すべてを必須にはしない。

#### B. 事例ネタ

旧ネタ帳をもとに次を入力可能にする。

- お客様の基本情報
- 何に困っていたか
- 導入前と導入後
- 何を提案したか
- 他に検討したもの
- 一番の壁
- どう乗り越えたか
- 誰に助けてもらったか
- お客様が言ってくれた言葉
- 自分が一番嬉しかったこと

これらをすべて必須入力にはしない。

#### C. 補足メモ

自由記述。

商談経緯、現場で起きたこと、営業担当者の判断・工夫、会話、感情、背景等を含められる。

単なる補足欄ではなく、案件理解に利用する正式なsourceとして扱う。

#### D. 資料

資料添付はMVP必須とする。

営業担当者は、PDF・画像・文書・表計算・テキスト等の案件資料を追加できること。

AIは資料だけを単独で解釈せず、入力項目、自由メモ、回答等とあわせて案件全体を理解する。

物理保存方式とOCR・テキスト抽出方式の基本構成は `docs/正本/技術選定理由書.md` を正本とする。対応形式、サイズ上限、件数上限、読取精度要件は実装前の設計確認で確定する。

読取に失敗した資料は未読として扱い、読めなかった内容をAIが推測で補わない。

OCR・抽出で判読不確実な箇所は、抽出結果に警告・要確認範囲を保持し、通常の確定sourceと同じ確度でAIへ渡さない。

### S-03 AI不足確認

目的:

AIが材料全体を理解した後、販売事例として本当に不足している価値の高い情報だけをまとめて確認する。

AIは質問生成前に少なくとも次をまとめて確認する。

- 初期入力
- 自由メモ
- 利用可能な添付資料
- 既存回答
- 既存fact
- 既に保留・回答済みとなっている質問状態

不足判定は、入力欄の空欄有無ではなく、少なくとも次の販売事例品質で行う。

- 課題の具体性
- 提案の具体性
- 採用理由
- 比較検討
- 因果関係
- 壁
- 突破
- 営業担当者の判断・工夫
- 結果・変化
- 顧客の言葉
- 再利用性・横展開性

質問生成ルール:

- 固定質問の順番消化にしない
- 既知情報を再質問しない
- 入力済み、資料に明示済み、回答済みの内容を再質問しない
- 質問0件を正常扱いする
- 必要な質問は原則1回分のバッチとしてまとめて提示する
- 固定件数上限を先に置いて重要情報を切り捨てない
- ただし極端に多い質問をそのまま表示しない
- 既知情報、重複、低価値、空欄を埋めるだけの質問、推測誘導、回答不能な抽象質問は表示前に除外する
- 「詳しく教えてください」「ほかにありますか」のような抽象質問ではなく、具体的に答えられる質問にする
- 分からない情報を無理に思い出させない

表示:

- AIが理解した案件の要点
- 追加で確認したい質問
- 各質問の理由または確認目的
- 回答欄
- 分からない
- 後で確認
- 今回は省略

質問0件の場合は、この画面を確認メッセージだけで通過できる。

各質問の回答状態:

- answered
- unknown
- later
- skipped

空欄とunknownは区別する。

laterは保留質問として残し、fact reviewへ進んだ後でも再表示して回答できる。

laterへ後日回答した場合は、その回答をsourceへ追加し、関連candidateを再評価する。

保留質問が残っていることだけを理由に編纂を禁止しない。

回答送信後、自動的に次の質問バッチを生成しない。

2回目以降の自動質問は通常フローでは発生させず、次の場合だけ許容する。

1. 1回目回答によって重大な矛盾が新たに生じた
2. 1回目回答によって新しい重要論点が判明し、それがないと事例因果が成立しない
3. 利用者が「追加取材」を明示的に実行した

単に未入力domainが残っていることを理由に2回目を出さない。

「分かりません」「意味が分かりません」「はい」「そう書きました」「後で確認します」等の会話制御返答を、そのままcandidate factにしない。

### S-04 事実確認

目的:

AIが抽出した事実候補を、人間が根拠とともに確認する。

AIが抽出した内容は必ずcandidateから開始し、AIだけの判断でconfirmedにしない。

confirmedへ変更できるのは、少なくとも次を満たす場合。

- 根拠sourceが存在する
- 対象caseが一致する
- 利用者が確認した
- AI推論だけではない

表示単位:

- 事実領域
- candidate本文
- 根拠抜粋
- 根拠元
- 状態
- 矛盾
- 類似candidate

操作:

- 確認
- 修正して確認
- 却下
- 要確認
- 手動追加
- 根拠を見る

根拠ルール:

- どの入力、回答、資料を根拠にしたか追跡できる
- 根拠抜粋を保持する
- 根拠のない数値、固有名詞、顧客発言、感情、効果を作らない
- OCR等で不確実なsourceを、確実な根拠と同じ扱いでconfirmed化しない

修正・履歴ルール:

- candidateを修正してconfirmedにする場合、元candidateを消さない
- 修正前candidateを履歴追跡可能にする
- confirmed factを後から修正する場合も新版を作る
- 旧版はsupersededとして保持する
- 物理削除だけで履歴を失わない
- 手動追加factも追加直後はcandidateとし、confirm操作を経てconfirmedにする

重複・衝突ルール:

1. 完全一致
2. 数値・固有名詞を除いた意味近似
3. 同domain内の意味重複
4. 既存confirmedとの衝突

同義candidateを大量に作らない。

会話の1文を機械的に多数のfactへ細切れにしない。

AI判定だけで既存factを破棄しない。

必要に応じて利用者へ統合候補を提示する。

編纂へ使えるのは原則confirmed factのみとする。

candidate、needs_check、rejected、根拠不明情報を確定本文の根拠へ混入させない。

未confirmed factや保留質問が残っていても、confirmed factだけで販売事例として成立する場合は編纂可能性を評価する。

confirmed factだけでは販売事例として成立しない場合は、何が不足しているかを利用者へ明示する。

### 4.1 S-02 / S-03 / S-04 具体UIレイアウト

#### S-02 事例入力

PC:

- 上段: お客様・案件基本情報
- 中段左: 事例ネタ入力
- 中段右: 自由メモ
- 右または下部の同一画面内: 資料添付一覧と追加操作
- 画面下部固定操作: 保存、AIで整理する

スマートフォン:

- 1カラム
- 基本情報 → 事例ネタ → 自由メモ → 資料添付 → 操作ボタンの順
- 長い入力を失わないよう各領域を個別保存可能にする

#### S-03 AI不足確認

PC / スマートフォン共通:

- 上部: AIが理解した案件要点
- その下: 質問を縦に一覧表示
- 各質問は「質問文」「確認目的」「回答欄」「分からない」「後で確認」「今回は省略」を同じまとまりに置く
- 1問ずつ別画面へ遷移させない
- 下部固定操作: 一時保存、回答を確定してfact確認へ進む
- 質問0件の場合は要点確認とfact確認へ進む操作だけを表示する

#### S-04 事実確認

PC:

- 左側: fact候補一覧
- 右側: 選択factの根拠詳細パネル
- fact候補には事実領域、本文、状態、矛盾・重複警告を表示
- 各factの主要操作は「確認」「修正して確認」「却下」「要確認」
- 手動追加は一覧上部または下部の副操作
- 根拠パネルでは根拠元、根拠抜粋、該当資料を確認できる

スマートフォン:

- fact候補を縦カード表示
- 根拠はカード内展開または下部ドロワーで表示
- 主要4操作は候補ごとに固定位置へ置く

共通:

- candidate / confirmed / rejected / needs_checkを視覚的に区別する
- 矛盾・類似candidateは警告として表示するが、AIだけで自動統合・自動破棄しない
- 保留質問へ戻る導線をfact確認画面から利用できる

### S-05 編纂確認

目的:

confirmed factのみから生成した完成事例を確認する。

表示:

- タイトル
- 顧客背景
- 課題
- 提案内容
- 選定理由
- 比較検討
- 壁
- 突破
- 結果
- 顧客の言葉
- 営業担当者の判断・工夫
- 社内外連携
- 担当者の喜び
- 成功要因
- 注意点
- 刺さる顧客像
- 横展開
- ストーリー

操作:

- 表現修正
- 再編纂
- 事実確認へ戻る
- 公開へ進む

新事実を本文へ直接追加するUIにはしない。

### S-06 承認（将来用・MVPでは未使用）

MVPでは承認画面・承認操作を通常フローに出さない。

将来、上司確認等の承認運用を有効化できるよう、承認状態・承認者・承認日時等を持てる設計余地だけ確保する。

MVPの通常フローは次とする。

```text
編纂確認済み → 公開
```

将来承認を有効化する場合は、要件定義書・本書・API一覧を改訂してから実装する。

### S-08 事例詳細

営業利用者向けに以下を表示する。

- 完成ストーリー
- 顧客背景
- 課題
- 提案
- 結果
- 壁と突破
- 顧客の言葉
- 営業担当者の工夫
- 横展開

#### コメント

公開済み事例ではコメント欄を表示する。

- 認証済み社内利用者はコメント一覧を閲覧・投稿可能
- 自分のコメントは編集・削除可能
- admin / sysadminは管理上必要な削除が可能
- コメントはconfirmed factではなく、販売事例本文の根拠に自動利用しない
- コメントを本文へ反映する場合は、作成者が改訂を開始しfact確認フローを通す
- 公開停止中はコメント欄を通常利用者へ表示せず、新規投稿も受け付けない

内部のcandidate一覧、AIログ、エラー情報等は管理用UIへ分離する。

### S-09 印刷・PDF

A4印刷・PDF出力はMVP必須とする。

**A4縦1ページ、1事例1ページ** とする。

画面をそのまま印刷せず、営業利用向けの専用レイアウトを正本データから生成する。

レイアウト:

- 上部: タイトル、顧客プロフィール、案件要点
- 左カラム: 課題、提案、採用理由、Before/After、成果
- 右カラム: 営業ストーリー、壁と突破、顧客の言葉、横展開ポイント
- 下部: 注意点、公開版・出力版識別情報
- コメントは掲載しない

情報が多い場合は文字サイズ縮小だけで詰め込まず、項目優先度と要約ルールで1ページへ収める。

HTMLテンプレート自体を正本データにはしない。

MVPでは社内利用版を対象とし、匿名共有版は対象外とする。

### S-10 管理

adminの管理範囲:

- 利用者の有効 / 無効
- role
- 所属・拠点
- 業務マスター
- 公開状態
- コメント管理削除
- audit / activity / error log閲覧
- 全案件の管理者向け状態確認
- アーカイブ・復元

sysadminはadmin権限に加えて次を扱う。

- system setting
- 障害調査・復旧
- 技術設定
- 外部連携設定

MVPで管理画面から編集できる業務マスター:

- 顧客業種・業態
- 機械分類
- メーカー

拠点・所属は利用者管理側の組織情報として扱う。

次は自由編集マスターにしない。

- fact domain
- 状態値
- 権限種別
- 質問制御
- 編纂section
- 公開状態値

これらを変更する場合は正本改訂を伴う。

admin / sysadminであってもconfirmed-only編纂を迂回せず、factや編纂本文を管理画面から直接書き換えない。秘密値も画面表示しない。

## 5. 案件状態

案件は次の状態を基本とする。

```text
draft
  ↓
ready_for_ai
  ↓
questioning
  ↓
fact_review
  ↓
compilation_review
  ↓
published
```

補助状態:

- archived
- suspended

### 5.1 draft

入力途中。

### 5.2 ready_for_ai

AI案件理解を実行可能な状態。

### 5.3 questioning

不足質問がある状態。

不足質問0件の場合、この状態を通らずfact_reviewへ進める。

### 5.4 fact_review

candidate fact確認中。

### 5.5 compilation_review

confirmed factをもとに編纂済みで、確認中。

### 5.6 published

検索・閲覧対象。

### 5.7 archived

通常利用から除外。

### 5.8 suspended

一時停止状態。削除・完了ではなく、再開可能な案件として保持する。

停止前の状態を `suspended_from_state` として保持し、再開時にその状態へ戻す。

### 5.9 状態遷移ルール

### draft → ready_for_ai

S-02で利用者が「AIで整理する」を実行した時に遷移する。

遷移前に、AIへ渡せるsourceが1件以上存在することを検証する。

### compilation_review → fact_review

S-05の「事実確認へ戻る」で遷移する。

現在の編纂版は削除せず保持する。fact変更後は新しい編纂版を作成する。

### published → fact_review（改訂開始）

公開済み事例の改訂を開始する場合に遷移する。

この時点では既存publicationを維持し、検索・閲覧では旧公開版を継続表示する。

新しい編纂版を確認して再公開した時点で、publicationが新しいcompilationへ差し替わる。

### unpublish後

公開停止はpublicationを停止し、検索索引から除外する。

caseの作業状態は原則として変更しない。

ただし、case.status=`published` で改訂作業を開始していない案件を公開停止した場合のみ、再確認可能な `compilation_review` へ戻す。

改訂中で case.status=`fact_review` または `compilation_review` の場合は、その作業状態を維持する。

### suspended

draft / ready_for_ai / questioning / fact_review / compilation_review から停止可能とする。

publishedの単純停止は `unpublish` を使用し、suspendedとは分ける。

## 8. fact設計

- confirmed

- needs_check

### 8.1 confirmed条件

confirmedへ変更できるのは、以下を満たす場合。

- 根拠sourceが存在する
- 対象caseが一致する
- 利用者が確認した
- AI推論だけではない

### 8.2 修正

candidateを修正してconfirmedにする場合、元candidateを消さず、履歴追跡可能にする。

confirmed factを後から修正する場合も、新版を作り旧版をsupersededとする。

### 8.3 重複

同義candidateが既存の場合、新規factを機械的に増やさない。

処理方針:

1. 完全一致
2. 数値・固有名詞を除いた意味近似
3. 同domain内の意味重複
4. 既存confirmedとの衝突

AI判定だけで既存factを破棄せず、必要に応じて利用者へ統合候補を提示する。

## 9. AI案件理解設計

AI案件理解は、単一の質問生成APIではなく、案件全体評価処理とする。

論理処理:

```text
1. source収集
2. 既存fact収集
3. 既回答・質問状態収集
4. 案件文脈生成
5. candidate抽出
6. candidate正規化
7. 重複・衝突検査
8. 事例品質評価
9. 不足情報評価
10. 質問バッチ生成
```

### 9.1 文脈

AIへ渡す文脈は、案件内の必要情報に限定する。

無関係な他案件、秘密値、内部ログ全文を送らない。

### 9.2 不足評価

不足はdomain空欄ではなく、販売事例品質から評価する。

評価軸:

- 課題の具体性
- 提案の具体性
- 採用理由
- 因果関係
- 壁
- 突破
- 営業判断
- 結果
- 顧客の言葉
- 再利用性

### 9.3 質問生成

質問は1回分のバッチとして生成する。

固定件数上限は持たせない。

ただし、表示前に以下を除外する。

- 既知情報
- 回答済み情報
- 同義重複
- 空欄を埋めるだけの低価値質問
- 推測を誘導する質問
- 回答不能な抽象質問

### 9.4 2回目の質問

2回目以降の自動質問は通常フローでは発生させない。

以下の場合のみ許容する。

1. 1回目回答によって重大な矛盾が新たに生じた
2. 1回目回答によって新しい重要論点が判明し、それがないと事例因果が成立しない
3. 利用者が「追加取材」を明示的に実行した

単に未入力domainが残っているという理由では2回目を出さない。

### 10.1 後で確認の扱い

disposition=`later` の質問は保留質問として残す。

fact_reviewへ進んだ後でも保留質問一覧から再表示できること。

後から回答した場合は、その回答をsourceへ追加し、関連candidateを再評価する。

保留質問が残っていることだけを理由に編纂を禁止しない。編纂可能性はconfirmed factの内容で判断する。

## 11. 会話上の非事実抑止

以下のような返答は、そのままcandidate factにしない。

- 分かりません
- 意味が分かりません
- はい
- そう書きました
- その質問は何の関係がありますか
- 後で確認します

これらは、質問理解、回答状態、UIメッセージとして扱う。

AIが事実候補として抽出した場合、candidate検証で除外する。

## 14. 公開設計

公開対象は、利用者が編纂確認を完了した編纂版とする。MVPでは承認を必須としない。

公開時に検索索引を同時生成する。

```text

  ↓

  ↓

  ↓

```

途中失敗時に「publishedなのに索引がない」状態を作らない。

公開停止時は検索対象から除外する。

## 15. 公開範囲

MVPの基本公開範囲は「社内利用」とし、社内の認証済み利用者は所属拠点・部門に関係なく公開済み販売事例を全社横断で検索・閲覧できる。

publicationは少なくとも次の表示設定を持つ。

- visibility: internal
- show_customer_name
- show_amounts

MVPの値は `internal / true / true` を標準とし、一般利用者向けの表示切替UIは設けない。

`show_customer_name` / `show_amounts` は将来の表示制御拡張に備えて保持する。将来これらをfalseにする場合も、顧客名・金額がカード、詳細、検索索引、印刷/PDFから漏れないようサーバー側で一貫して適用する。

匿名共有版はMVP対象外とする。

MVPの公開対象は社内利用のみとし、権限ある利用者には確認済みの顧客名・金額を通常表示できることを基本とする。

社外公開は行わない。

## 18. 権限設計

MVPの基本ロールを以下とする。

### salesperson

- 自分の案件作成
- 自分の案件編集
- candidate確認
- 編纂確認
- 公開済み事例検索・閲覧
- 公開済み事例へのコメント投稿
- 自分のコメント編集・削除

### manager

MVPでは公開済み販売事例の閲覧範囲をsalespersonと分けない。

- 社内公開済み販売事例を全社横断で検索・閲覧
- 自分の案件はsalespersonと同様に作成・編集

MVPでは「管轄案件だけを閲覧する」「所属拠点・部門で閲覧範囲を制限する」機能は設けない。

manager固有の閲覧制御は作らない。コメント機能はmanager専用ではなく、認証済み社内利用者の共通機能とする。

### admin

- 利用者管理
- マスター管理
- 公開状態管理
- コメント管理削除
- ログ・エラー確認
- 全案件管理

### sysadmin

adminに加え、

- システム設定
- 障害対応
- 技術設定

### 18.1 認可原則

権限制御はサーバー側で行う。

クライアントがowner、role、branch等を書き換えても権限を突破できないこと。

### 18.2 権限の基本方針

MVPでは公開済み販売事例の閲覧範囲を拠点・部門・上下関係で制限しない。

- 社内公開済み販売事例: 社内の認証済み利用者が全社横断で検索・閲覧できる
- 作成途中案件: 原則として作成者本人が編集する
- 自分の販売事例の公開・公開停止: 作成者本人が実行できる
- 管理操作: admin / sysadmin に限定する

manager専用の「管轄案件閲覧」機能はMVPでは設けない。

認証方式とrole連携の基本方式は確定済みとする。残る権限設計上の未確定事項は、admin / sysadminの詳細管理範囲である。

## 19. 認証

認証方式は `docs/正本/技術選定理由書.md` に従い、Google Workspaceアカウントを用いたGoogle OpenID Connectを基本とする。

アプリ側の利用者マスターでGoogleアカウント識別子とroleを紐づけ、社内利用者であることとアプリ利用権限をサーバー側で検証する。

以下を必須とする。

- 利用者を一意に識別できる
- roleと所属をサーバー側で確定できる
- 認証情報をクライアントへ過剰露出しない

## 20. 競合制御

対象:

- 案件入力
- fact変更
- 編纂修正
- 公開

- 管理設定

クライアントは取得時versionを送る。

サーバー側versionと一致しない場合はCONFLICTとして更新しない。

自動上書きしない。

## 25. 分析設計

MVPでは最低限の運用改善ログを扱える構造にする。

人気ランキング・営業担当ランキング等のランキング機能はMVP対象外とする。

最低限、以下を集計する。

- 作成開始件数
- AI理解実行件数
- 質問発生率
- 質問0件率
- 回答完了率
- fact確認完了率
- 編纂完了率
- 公開率
- 途中離脱
- 再開
- 検索回数
- 0件検索
- 事例閲覧
- コメント投稿件数
- コメント編集件数
- コメント削除件数

「途中離脱」は直接の単一イベントではなく、次をすべて満たす案件を集計時に判定する派生指標とする。

- archivedではない
- suspendedではない
- 有効なpublicationが存在しない
- 設定された一定期間、進行イベントがない

進行イベントは、`input_saved`、`case_marked_ready_for_ai`、`ai_understanding_started`、`question_batch_answered`、`deferred_question_answered`、`fact_review_started`、`fact_review_reopened`、`fact_confirmed`、`fact_rejected`、`fact_marked_needs_check`、`compilation_generated`、`compilation_review_completed`、`case_revision_started`、`case_published`、`case_unpublished`、`case_resumed` とする。

判定期間の初期値は **14日** とする。

最終進行イベントから14日以上進行がない案件を途中離脱候補とする。

有効なpublicationがある改訂中案件とsuspended案件は途中離脱候補から除外する。

判定期間はsystem settingとして保持し、MVPではsysadminだけが変更可能とする。

ただし、質問数やfact数だけで品質評価しない。

## 26. A4/PDF設計

A4/PDFはMVP必須とする。

**A4縦1ページ、1事例1ページ** とする。

正本データから印刷専用ViewModelを生成する。

配置:

- 上部: タイトル、顧客プロフィール、案件要点
- 左カラム: 課題、提案、採用理由、Before/After、成果
- 右カラム: 営業ストーリー、壁と突破、顧客の言葉、横展開ポイント
- 下部: 注意点、公開版・出力版識別情報

コメントはA4/PDFへ含めない。

情報量が多い場合は文字サイズを極端に縮小せず、表示優先度と要約ルールで1ページに収める。

旧HTMLのCSS・構造をそのまま正本にはしない。

複数事例の一括出力はMVP対象外とする。

## 27. 資料添付設計

資料添付はMVP必須とする。

MVP対応形式:

- PDF
- JPG / JPEG
- PNG
- DOCX
- XLSX
- PPTX
- TXT
- CSV

上限:

- 1ファイル最大20MB
- 1案件あたり有効添付最大10ファイル
- 1案件あたり最大合計200MB

画像PDF、JPG/JPEG、PNGの文字読取にはGoogle Cloud Document AI Enterprise Document OCRを使用する。

許可形式外、上限超過、破損ファイルは明示的に拒否する。

論理的には以下の構造とする。

```text
attachment
  ├─ metadata
  ├─ storage reference
  ├─ extraction status
  ├─ extracted text
  └─ evidence ranges
```

ファイルバイナリはDB本体へ直接保持せず、`docs/正本/技術選定理由書.md` に従いGoogle Cloud Storageへ保存し、DBにはattachment metadataとstorage keyを保持する。

## 33. MVPで確定した設計判断

現時点で本書により確定する。

- 旧ネタ帳10領域を標準入力骨格として採用する
- 全項目必須にはしない
- AIは案件全体を見て不足を評価する
- 不足質問は原則1回のバッチ
- 質問0件を正常とする
- 2回目質問は例外条件のみ
- AI抽出はcandidateから始める
- confirmedは人間確認が必要
- confirmedだけを編纂根拠にする
- fact_id相当の根拠追跡を持つ
- 編纂版を履歴管理する
- 検索は構造化 + 全文を基本とする
- ベクトル検索はMVP必須ではない
- 公開時に検索索引を生成する
- 営業利用画面と内部管理画面を分ける
- 重要更新は競合検出する
- 技術構成は技術選定理由書を正本とし、旧実装を理由に変更しない
