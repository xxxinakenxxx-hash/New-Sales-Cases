## 4. 編纂

confirmed factだけを入力に使う。

編纂構造:

- title
- customer_background
- problem
- proposal
- selection_reason
- alternatives
- barrier
- breakthrough
- salesperson_judgment
- collaboration
- before_after
- result
- customer_quote
- salesperson_joy
- success_factor
- caution
- target_customer
- reuse_point
- story

各sectionから使用したfact_idを追跡できること。

必須検査:

- 未confirmed fact参照
- 架空数値
- 架空顧客発言
- 架空固有名詞
- 根拠のない感情
- 提案と採用理由の混同
- 因果飛躍

ストーリーは「課題 → 壁 → 突破 → 成果 → 喜び」の因果を読めるものとし、営業担当者の言葉・温度感を不必要に変換しない。

## 6. 公開

MVPでは承認フローを使わない。

公開条件:

- compilation review完了
- compilation source valid
- case権限valid

公開時:

- visibility=internal
- showCustomerName=true
- showAmounts=true
- 検索索引を同時生成
- publicationとsearch indexを論理的に一体更新

「publishedなのに検索索引がない」状態を作らない。

公開停止時:

- 検索対象から除外
- compilation / fact / commentは保持
- 改訂中状態を壊さない

改訂:

- 公開中の旧publicationを維持
- 新版のfact review → compilation → review完了
- 再公開時にpublicationを新版へ差替え
- 過去compilation保持
- comment保持

## 9. コメント

公開済みcaseだけを対象にする。

操作:

- 一覧
- 投稿
- 自分のコメント編集
- 自分のコメント削除
- admin / sysadmin管理削除

ルール:

- case単位保持
- 投稿時publicationId記録
- version競合検出
- 改訂・再公開後も保持
- 公開停止中は通常表示・新規投稿停止
- 再公開後に再表示
- fact / source / compilationへ自動投入しない
- A4/PDFへ含めない
- 検索索引へ含めない

## 10. A4 / PDF

**A4縦1ページ、1事例1ページ**。

画面DOMをそのまま印刷しない。

専用ViewModel:

- 上部: タイトル、顧客プロフィール、案件要点
- 左: 課題、提案、採用理由、Before/After、成果
- 右: 営業ストーリー、壁と突破、顧客の言葉、横展開
- 下部: 注意点、公開版・出力版識別情報

情報量が多い場合は文字サイズを極端に縮小せず、優先順位・要約ルールで1ページに収める。

PDF:

- headless Chromium系
- 日本語崩れ・文字切れなし
- publication / compilation version追跡
- コメントなし
- 1事例単位のみ
