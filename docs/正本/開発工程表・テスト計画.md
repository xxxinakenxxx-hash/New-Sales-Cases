## 1. 本書の目的

本書は「新販売事例」MVPを、正本で確定した業務価値単位に分けて実装・検査するための開発工程とテスト計画を定義する。

本書は旧「機械販売事例まとめアプリ」の工程番号、旧コード構成、旧API構成を自動継承しない。

実装はChatGPTが正本・実装結果を確認し、Claude Codeへ工程単位で指示し、各工程の受入条件を満たしたことを確認してから次へ進む。

## 2. 開発の基本原則

### 2.1 工程は業務価値単位で切る

UIだけ、DBだけ、APIだけを独立工程にしない。

各工程は、利用者が実際に確認できる業務の流れとして完結させる。

### 2.2 技術テストだけで完了にしない

AI取材、事実確認、編纂品質、検索再利用性は、関数が正常終了しただけでは合格にしない。

実際の販売事例を使った実機確認を必須とする。

### 2.3 上位正本を実装都合で変更しない

実装上の都合で要件を削らない。

設計変更が必要になった場合は、Claude Codeが独自判断せず、ChatGPTが正本変更要否を判断してから実装指示を更新する。

### 2.4 次工程へ自動で進まない

各工程の完了後、ChatGPTが以下を確認する。

1. 変更ファイル
2. テスト結果
3. 正本との整合
4. 未解決事項
5. 実機確認が必要な項目
6. 次工程へ進めるか

## 3. MVP工程構成

MVPは、設計完了後に実装3工程 + MVP完了判定で進める。

| 区分 | 工程 | 主目的 |
| --- | --- | --- |
| P1 | 事例作成コア | 入力→資料→AI理解→不足確認→fact確認を完成させる |
| P2 | 事例完成・公開・再利用 | 編纂→公開→検索→詳細→コメント→A4/PDFを完成させる |
| P3 | 管理・運用品質・総合テスト | 管理、ログ、セキュリティ、復旧、実機品質を完成させる |
| MVP | 完了判定 | 正本のMVP受入条件をすべて満たすか判定する |

P1〜P3は、それぞれ独立した実装指示書を作成する。

## 4. 実装開始前の設計完了条件

実装工程へ入る前に、以下が正本として確定していること。

- 案件概要書
- 要件定義書
- 統合設計書
- API・内部関数一覧
- 技術選定理由書
- 開発工程表・テスト計画

未確定事項の管理先は `docs/記録/未確定事項確認書_2026-10-14.md` とする。

P1実装指示書を確定する時点で、P1着手を妨げる未確定事項が同確認書に残っていないことをChatGPTが確認する。

未確定事項を本工程表へ重複列挙しない。

## 5. P1 事例作成コア

### 5.1 目的

営業担当者が分かる範囲の材料を入力し、資料を追加し、AIが案件全体を理解して不足だけを確認し、人間確認済みの事実を作れる状態まで完成させる。

### 5.2 対象画面

- S-01 ホーム・案件一覧の作成途中領域
- S-02 事例入力
- S-03 AI不足確認
- S-04 事実確認

### 5.3 対象機能

#### Case

- 新規作成
- 入力保存
- AI実行可能化
- 作成途中一覧
- 中断・再開
- 一時停止・再開
- optimistic version競合
- アーカイブ・復元の基礎

#### Input / Source

- 旧ネタ帳10領域を標準入力骨格として扱う
- 全項目必須にしない
- 自由メモ
- source保存
- source version
- manual fact source

#### Attachment

- 資料添付
- metadata保存
- 抽出状態
- PDF / 画像 / 文書 / 表計算 / テキストの採用形式
- OCR / text extraction
- 読取失敗
- 判読不確実箇所の要確認表示
- 再抽出
- confirmed fact参照中資料の削除拒否

#### AI案件理解

- 案件全体のsource収集
- candidate fact抽出
- candidate正規化
- semantic重複抑止
- fact conflict検出
- 不足情報評価
- 質問バッチ生成
- 質問0件正常系

#### 不足確認

- 原則1回の質問バッチ
- 回答済み / 分からない / 後で確認 / 今回は省略
- 保留質問の再回答
- 2回目質問は例外条件のみ
- 回答後に自動で次質問を生成しない
- fixed fallback質問連鎖を作らない

#### Fact Review

- candidate
- confirmed
- rejected
- needs_check
- 修正してconfirmed
- manual fact追加
- duplicate merge
- superseded履歴
- evidence/source追跡
- 非事実返答の除外

### 5.4 P1で禁止する実装

- AI抽出を自動confirmedにする
- 1問回答ごとに次質問を自動生成する
- semantic重複で質問が消えた後に固定fallbackを順番に出す
- 会話制御返答をfact化する
- source本文をAI抽出結果で上書きする
- fact数・質問数を品質スコアとして使う

### 5.5 P1テスト計画

#### T1-01 新規作成・保存

確認:

- 空欄を含んだ状態でも保存できる
- 全項目入力を強制しない
- 保存後に再取得できる
- case versionが更新される

合格条件:

入力内容を失わず再開できる。

#### T1-02 version競合

手順:

1. 同じcaseを2画面で取得
2. 片方を更新
3. 古いversionでもう片方を更新

合格条件:

- 後勝ちで自動上書きしない
- CONFLICTを返す
- 最新状態を取得し直せる

#### T1-03 添付資料

最低ケース:

- 正常PDF
- 画像
- 文書
- 表計算
- テキスト
- 読取不能ファイル
- 非対応形式
- 上限超過

合格条件:

- 正常資料はsource化できる
- 読取失敗資料を特定できる
- 判読不確実な箇所を確定原文として扱わず、要確認状態を示せる
- 他の正常sourceは失わない
- 読めない内容をAIが推測しない

#### T1-04 AI案件理解

実案件材料を用いて確認する。

合格条件:

- 入力欄、メモ、回答、資料を案件単位でまとめて見る
- 既知情報を再質問しない
- candidateにsource/evidenceがある
- 同義candidateが大量発生しない
- 会話上の返答をcandidate化しない

#### T1-05 質問0件

十分な材料を入れてAI理解を実行する。

合格条件:

- エラーにならない
- QuestionBatchDTOは `questions: []`
- statusは `not_required`
- fact_reviewへ進める

#### T1-06 質問あり

不足を含む案件で実行する。

合格条件:

- 空欄順ではなく販売事例価値の高い不足を聞く
- 既知情報を聞き直さない
- 「詳しく教えてください」だけの抽象質問を避ける
- 質問を原則1回にまとめる
- 重要でない質問を大量表示しない

#### T1-07 回答状態

4状態を確認する。

- answered
- unknown
- later
- skipped

合格条件:

- 空欄と明示状態を区別
- laterは保留として残る
- laterはfact_review後にも回答可能
- unknown / skippedを事実扱いしない

#### T1-08 2回目質問

確認ケース:

- 新たな重大矛盾
- 新しい重要論点
- 利用者の明示要求
- 上記以外

合格条件:

上記3条件以外では2回目を自動生成しない。

#### T1-09 fact状態変更

確認:

- candidate → confirmed
- candidate → rejected
- candidate → needs_check
- edit + confirmed
- manual fact追加
- duplicate merge

合格条件:

- AIだけではconfirmed不可
- 旧版・元factを追跡可能
- rejected / needs_checkは編纂対象にならない

#### T1-10 根拠なしconfirmed拒否

合格条件:

source/evidenceが必要なfactで根拠がない場合はconfirmed化できない。

#### T1-11 非事実抑止

入力例:

- 分かりません
- 意味が分かりません
- はい
- そう書きました
- その質問は何の関係がありますか

合格条件:

上記返答を販売事実としてcandidate化しない。

### 5.6 P1実機品質確認

最低3案件で実施する。

案件は次を含める。

1. 材料が十分で質問0件になる案件
2. 一部不足があり質問が必要な案件
3. 資料添付を主材料とする案件

確認者:

- 事例作成者
- ChatGPTによる正本照合
- 必要に応じて別営業担当者

評価:

- 入力負担
- 不要な再質問
- 質問の意味
- candidateの重複
- source/evidenceの妥当性
- 人が確認しやすいfact粒度

### 5.7 P1完了条件

- T1-01〜T1-11が合格
- 重大エラーなし
- 実機3案件で旧プロジェクトの逐次質問・fallback連鎖が再発しない
- candidate乱立が実用上問題ない
- confirmed factまで一連で作成できる
- 中断・再開できる
- ChatGPTが正本との整合を確認
- ユーザー実機確認が必要な項目を提示し、重大問題がない

P1未完了のまま編纂・公開工程へ進まない。

## 6. P2 事例完成・公開・再利用

### 6.1 目的

confirmed factだけを使って販売事例を完成し、社内公開し、全社から検索・閲覧・コメント・印刷・PDF利用できる状態まで完成させる。

### 6.2 対象画面

- S-05 編纂確認
- S-06 承認（MVPでは未使用）
- S-07 検索・カード一覧
- S-08 事例詳細
- S-09 印刷・PDF

### 6.3 対象機能

#### Compilation

- readiness評価
- confirmed facts収集
- 編纂
- used fact refs
- 創作検査
- 編纂版管理
- 表現修正
- 再編纂
- 事実確認へ戻る

#### 完成事例の品質

最低限、次を扱う。

- title
- customer_background
- problem
- proposal
- selection_reason
- alternatives
- barrier
- breakthrough
- salesperson_judgment
- collaboration
- before_after
- result
- customer_quote
- salesperson_joy
- success_factor
- caution
- target_customer
- reuse_point
- story

ストーリーは単なる項目連結ではなく、課題→壁→突破→成果→喜びの因果を読める内容とする。

#### Publication

- 編纂確認後に社内公開
- 承認フローは使わない
- 公開停止
- 再公開
- 公開済み事例の改訂
- 改訂中も旧publicationを維持
- showCustomerName / showAmounts
- 社内全社横断閲覧
- 公開時検索索引生成

#### Search

- 構造化検索
- 全文検索
- カード一覧
- 事例詳細
- 検索0件
- 公開停止事例の除外

構造化検索の対象:

- 業種・業態
- 課題
- 対象工程
- 機械分類・機械名
- メーカー
- 提案内容
- 採用理由
- 導入効果
- 壁・突破
- 成功要因
- 刺さる顧客像
- 横展開ポイント
- 拠点
- 時期

ベクトル検索はMVPでは実装しない。

#### Comment

- 公開済み事例のコメント一覧
- 投稿
- 自分のコメント編集
- 自分のコメント削除
- admin / sysadmin管理削除
- case単位保持
- 投稿時publicationId記録
- 改訂後も保持
- 公開停止中は表示・新規投稿停止
- 再公開後に再表示
- fact/本文へ自動反映しない

#### A4 / PDF

- 1事例単位
- 正本データからViewModel生成
- 社内利用版
- 印刷プレビュー
- PDF生成
- 出力時compilation/publication version記録

匿名版、複数事例一括PDFはMVP対象外。

### 6.4 P2テスト計画

#### T2-01 confirmed-only編纂

合格条件:

- candidate / rejected / needs_checkを本文根拠に使わない
- usedFactIdsを追跡できる

#### T2-02 創作防止

検査:

- 架空数値
- 架空顧客発言
- 架空固有名詞
- 根拠のない感情
- 因果飛躍
- 提案と採用理由の混同

合格条件:

confirmed factで裏付けられない内容を確定本文へ入れない。

#### T2-03 編纂品質

実案件で確認する。

合格条件:

- 課題→壁→突破→成果→喜びが読める
- 営業担当者の判断・工夫が分かる
- 言葉・温度感を不必要にコンサル用語へ変えない
- 他営業が横展開の可能性を判断できる

#### T2-04 表現修正と新事実

合格条件:

- 表現だけの修正は保存可能
- 新事実混入を検知した場合は直接保存せずfact reviewへ戻す

#### T2-05 再編纂・版管理

合格条件:

- 新versionを作成
- 過去versionを保持
- どのversionが公開中か追跡できる

#### T2-06 公開

合格条件:

- compilation review完了前は公開不可
- 承認は要求しない
- publicationと検索索引が不整合にならない
- 公開後、全社認証済み利用者が検索・閲覧できる

#### T2-07 公開停止

合格条件:

- 検索結果から消える
- コメント表示・新規投稿を停止
- compilation、fact、コメントデータは失わない

#### T2-08 公開済み事例の改訂

手順:

1. 公開
2. 改訂開始
3. fact変更
4. 再編纂
5. 再公開

合格条件:

- 改訂中は旧公開版を閲覧可能
- 新版公開時にpublicationを差し替える
- 過去compilationを保持
- コメントを保持

#### T2-09 構造化検索

各フィルタ条件で確認する。

合格条件:

指定条件に対応した公開事例だけを返す。

#### T2-10 全文検索

合格条件:

完成編纂・confirmed fact・検索用要約を検索対象にできる。

#### T2-11 権限制限なしの全社閲覧

合格条件:

公開済み販売事例は、拠点・部門・manager管轄によって検索結果から除外されない。

#### T2-12 コメント

確認:

- 一覧
- 投稿
- 編集
- 削除
- 他人コメント編集拒否
- admin削除
- 改訂後保持
- 公開停止中拒否
- 再公開後再表示

合格条件:

正本のコメントライフサイクルどおり動作する。

#### T2-13 コメント非fact化

合格条件:

コメント投稿だけではsource / candidate / confirmed / compilationが変化しない。

#### T2-14 A4印刷

合格条件:

- 1事例単位でA4印刷できる
- 主要内容が欠落しない
- 画面用UIをそのまま印刷するだけではない
- 正本データから再生成可能

#### T2-15 PDF

合格条件:

- PDF生成成功
- 日本語崩れ・文字切れがない
- 架空情報が入らない
- 出力元versionを追跡できる

### 6.5 P2実機品質確認

最低3案件を使う。

確認:

- 完成事例として読み物になるか
- 営業担当者本人が「自分の案件」と認識できるか
- 別営業が「自分の顧客に使えそう」と判断できるか
- 検索で目的事例へ到達できるか
- A4/PDFを営業活動で使えるか
- コメントが事例の再利用を妨げず補助できるか

### 6.6 P2完了条件

- T2-01〜T2-15合格
- 実機品質確認で重大問題なし
- confirmed-only編纂が守られている
- 社内公開・検索・閲覧・コメント・A4/PDFが一連で動く
- コメントがfactへ自動混入しない
- ChatGPTが正本との整合を確認

管理機能、ログ、監査、エラー処理、セキュリティ、スマートフォン対応、障害復旧を含め、MVPを実運用できる品質まで引き上げる。

### 7.2 対象画面

- S-01〜S-10全体
- S-10 管理

### 7.3 対象機能

#### Admin

- role
- マスター
- システム設定
- 公開状態管理
- コメント管理削除
- 監査ログ
- 業務ログ
- エラーログ
- 案件管理

manager専用の「管轄案件閲覧」は作らない。

#### Responsive

### 7.4 P3テスト計画

#### T3-01 認証

合格条件:

- 未認証利用者を拒否
- 利用者を一意に識別
- roleをクライアント入力だけで信用しない

#### T3-02 下書き保護

合格条件:

他人の作成途中案件を通常利用者がID指定で取得・更新できない。

#### T3-03 公開済み事例閲覧

合格条件:

認証済み社内利用者は公開済み事例を全社横断で閲覧できる。

#### T3-04 コメント権限

合格条件:

- 投稿者だけが自分のコメントを編集・削除
- admin / sysadminは管理削除可能
- 一般利用者は他人コメントを変更不可

#### T3-05 XSS / 入力安全性

コメント、メモ、顧客名等へスクリプト文字列を入力する。

合格条件:

画面で実行されず、安全に表示される。

#### T3-06 秘密情報

合格条件:

API key、access token、内部secretが画面・通常レスポンス・ログに出ない。

#### T3-07 ログ

合格条件:

主要イベントが記録され、source全文やAI応答全文など不要な機密データを保存しない。

#### T3-08 途中離脱

合格条件:

- archived除外
- suspended除外
- 有効publicationあり除外
- 所定期間進行なしのみ対象
- 進行イベント発生で離脱対象から外れる

#### T3-09 AI障害

合格条件:

AI失敗時も入力済みsourceを失わず再実行できる。

#### T3-10 添付障害

合格条件:

1ファイルの失敗で他sourceを壊さない。

#### T3-11 公開障害

公開処理途中で意図的に失敗させる。

合格条件:

`publishedなのに検索索引がない` 状態を作らない。

#### T3-12 二重送信

保存、回答、公開、コメント投稿等を連続実行する。

合格条件:

不必要な二重データを作らない。

#### T3-13 PC

主要フローをPCで確認する。

#### T3-14 スマートフォン

主要フローをスマートフォン幅で確認する。

合格条件:

横スクロール前提や操作不能にならない。

#### T3-15 ブラウザ更新・再ログイン

合格条件:

作成途中状態を失わず再開できる。

#### T3-16 監査

合格条件:

重要変更について、誰が、何を、いつ変更したか追跡できる。

### 7.5 P3完了条件

- T3-01〜T3-16合格
- 重大な権限漏れなし
- データ損失につながる障害なし
- PC・スマートフォン主要操作に致命的問題なし
- ログ・監査が運用に使える
- ChatGPTが総合結果を検査し、MVP最終判定へ進行可と判断する

## 9. AI販売事例品質テスト

### 9.1 目的

旧プロジェクトで最も問題だった「技術上は動くが、販売事例として使えない」を防ぐ。

### 9.2 評価対象

最低5案件。

案件種類を偏らせない。

例:

- 数値効果が明確な案件
- 数値効果がない案件
- 壁・突破が強い案件
- 資料中心の案件
- 情報不足が多い案件

### 9.3 評価者

最低限:

- 案件を知る営業担当者
- 案件を知らない別営業担当者
- ChatGPTによる正本照合

### 9.4 評価項目

5段階スコアだけで合否を機械決定しない。

確認する内容:

1. 事実が正しい
2. AI創作がない
3. 不要な再質問がない
4. 質問が具体的で意味が分かる
5. 営業担当者の判断・工夫が残る
6. 壁と突破が分かる
7. 成果が分かる
8. 顧客の言葉が原文性を保つ
9. 営業担当者の温度感が残る
10. 他営業が横展開を判断できる
11. 読み物として因果が通る
12. 入力・回答負担が許容範囲

### 9.5 不合格条件

次のいずれかが重大に発生した場合、MVP合格にしない。

- 架空数値
- 架空顧客発言
- 根拠のない感情
- 既知情報の繰り返し質問
- 逐次質問の長期化
- fallback質問の連鎖
- 会話制御返答のfact化
- candidate大量重複
- confirmedでない情報の本文混入
- 営業担当者が「自分の案件と違う」と判断
- 別営業が再利用方法を理解できない

### 10.1 デプロイ責任とタイミング

- Claude Codeは実装・自動テスト完了後も自動でデプロイしない。
- ChatGPTが正本・差分・テスト結果を検査し、デプロイ可否を判定する。
- ユーザーの明示承認後にのみ、Claude Codeが指定環境へのデプロイを実行する。
- ユーザー自身が手作業でデプロイすることを標準運用にはしない。ただし、認証・権限上Claude Codeが実行できない場合は、ChatGPTが具体操作をユーザーへ依頼する。
- P1/P2/P3の実機確認は指定の検証環境で行い、MVP本番反映はMVP完了判定後に別途明示承認を得て実施する。
- デプロイ結果、対象環境、revision/version、実行者、日時をテスト証跡に記録する。

## 11. テスト証跡

Claude Codeは各工程で以下を `tasks/TASK_CURRENT.md` へ記録する。

- 実施した工程
- 変更ファイル
- 実装内容
- 実行したテスト
- テスト結果
- 失敗したテスト
- 未実施テスト
- 残件
- デプロイ先・version（該当する場合）
- commit / push情報

ChatGPTはClaude Code報告だけで完了判定せず、必要に応じてコード、テスト、実機結果を確認する。

## 12. 実機確認の扱い

自動テストで代替できないものは、ユーザー実機確認を行う。

主な対象:

- 入力負担
- AI質問品質
- 販売事例の読みやすさ
- 営業担当者らしい言葉
- 検索の探しやすさ
- スマートフォン操作
- A4/PDF
- コメント利用感

実機確認で重大問題が出た場合、技術テスト合格でも工程完了にしない。

## 13. MVP完了条件

MVP完了には以下をすべて満たすこと。

### 13.1 機能

- 入力
- 保存・再開
- 資料添付
- AI案件理解
- 不足質問
- 保留回答
- fact確認
- 編纂
- 編纂確認
- 公開
- 公開停止
- 改訂・再公開
- 検索
- 詳細閲覧
- コメント
- A4印刷
- PDF
- 管理
- 最低限の利用ログ

### 13.2 データ品質

- AI生成factはcandidateから始まる
- confirmedには人間確認がある
- source/evidenceを追跡できる
- 履歴を失わない
- confirmed-only編纂を守る
- コメントをfactへ自動混入しない

### 13.3 AI品質

- 既知情報を不必要に再質問しない
- 質問0件を正常扱い
- 原則1回の質問バッチ
- 2回目質問は例外条件のみ
- 固定fallback連鎖を使わない
- 非事実返答をfact化しない
- 架空情報を作らない

### 13.4 再利用品質

- 全社横断で公開済み事例を検索・閲覧できる
- 構造化検索と全文検索が使える
- 別営業が事例価値を一覧から判断できる
- 詳細から横展開ポイントを理解できる
- コメントで補足・質問・横展開アイデアを蓄積できる
- A4/PDFを営業利用できる

### 13.5 運用品質

- サーバー側認可
- version競合防止
- 重要変更の監査
- 秘密情報非露出
- 障害時に入力を失わない
- 公開と検索索引の整合
- PC・スマートフォン利用

### 13.6 MVP対象外を混入させない

MVPでは以下を作らない。

- 承認フロー実運用
- 匿名共有版
- ランキング
- 旧データ初期移行
- ベクトル検索
- 複数事例一括PDF
- manager専用の管轄案件閲覧

## 14. 工程完了判定

各工程の判定は次の3種類とする。

- 完了: 受入条件を満たし、次工程へ進行可
- 条件付き停止: 軽微な残件があるが次へ進めるかChatGPTが明示判断
- 未完了: 重大な仕様不一致、テスト失敗、未確認事項があり進行不可

「テストコードが通った」「Claude Codeが完了と報告した」だけでは完了にしない。
