## 1. 本書の目的

本書は、新販売事例を新規実装するための技術構成を、実装工程ではなく設計段階で決定し、その選定理由を固定する。

旧「機械販売事例まとめアプリ」のGAS・Googleスプレッドシート構成を前提にしない。

技術選定によって上位正本の業務要件を変更しない。

## 2. 選定の前提

本アプリには以下が必要である。

- PC・スマートフォン対応の社内Webアプリ
- source / fact / evidence / compilation / publication / comment の構造化保存
- 履歴・版管理
- optimistic version競合
- 資料添付
- PDF・画像・文書・表計算・テキストの読取
- OCR
- AIによる案件理解・不足質問・編纂
- 構造化検索 + 全文検索
- A4印刷・PDF生成
- Google Workspaceを利用する社内利用者の認証
- 管理・監査ログ
- GitHub + Claude Codeによる新規開発

## 3. 採用する基本構成

### 3.1 アプリケーション

採用:

- TypeScript
- Next.js系のReact Webアプリ
- サーバー処理を同一リポジトリ内のサーバー側モジュールとして実装
- コンテナ化してGoogle Cloud Runへ配置

理由:

- PC・スマートフォン向けレスポンシブWebを一つのコードベースで構築できる
- 画面・API・サーバー側業務ロジックをTypeScriptで統一しやすい
- GitHub + Claude Codeの開発フローと相性がよい
- GASの実行時間・UI・モジュール構成へ設計を寄せずに実装できる
- Cloud RunでAI処理、OCR連携、PDF生成等のサーバー処理を実装しやすい

### 3.2 ホスティング

採用:

Google Cloud Run

理由:

- コンテナ単位でWebアプリを配置できる
- 長期的にGAS固有制約へ依存しない
- Google Cloud Storage、Cloud SQL等と同一クラウド内で構成しやすい
- 開発・検証・本番を分離しやすい

### 3.3 DB

採用:

PostgreSQL + Google Cloud SQL

理由:

本アプリは単純な台帳ではなく、case、source、attachment、fact、evidence、question、answer、compilation、publication、comment、audit等の関係を持つ。

PostgreSQLを採用することで、

- transaction
- 外部キー
- 履歴
- version競合
- 構造化検索
- 全文検索
- 集計
- 将来のデータ拡張

を一つの基盤で扱いやすい。

Googleスプレッドシートを業務DBとしては使用しない。

### 3.4 ファイル保存

採用:

Google Cloud Storage

対象:

- 原本添付
- OCR・抽出対象ファイル
- 必要な派生成果物

方針:

- ファイルバイナリはDBへ直接保存しない
- DBにはattachment metadataとstorage keyを保持する
- クライアントへ内部storage keyを直接公開しない
- アクセスは認証・認可を通したダウンロードまたは期限付きURLで行う

### 3.5 認証

採用方針:

Google Workspaceアカウントを使ったGoogle OpenID Connect認証。

アプリ側ではDBに利用者マスターを持ち、Googleアカウント識別子とroleを紐づける。

MVP role:

- salesperson
- manager
- admin
- sysadmin

公開済み事例の閲覧はrole・拠点・部門で制限しない。

作成途中案件、編集、管理操作はサーバー側で認可する。

### 3.6 検索

採用:

- Cloud SQL for PostgreSQL 18
- PostgreSQLの構造化検索 + `pg_bigm` による日本語全文検索

理由:

- MVP要件は構造化検索 + 全文検索である
- 日本語は空白区切りを前提にした単純な全文検索だけでは検索品質が不足しうる
- `pg_bigm` は2-gram索引による全文検索を提供し、日本語を含む検索に適する
- case / fact / publicationと同じDB内で検索索引を管理できる
- 別検索基盤を増やさずMVPの運用複雑性を抑えられる
- Cloud SQLの現行公式仕様でPostgreSQL 18は標準サポートされ、`pg_bigm` もCloud SQLの対応拡張として提供されているため、MVPの基盤として固定する

実装時は `cloudsql.enable_pg_bigm=on` を有効化する。

代表的な日本語販売事例データで、部分一致・複合語・メーカー名・機械名・課題語等の検索品質を受入テストする。ただし、これは採用可否を再度ユーザーへ問う未確定事項ではなく、実装品質確認とする。

ベクトル検索はMVPでは実装しない。

### 3.7 AI連携

採用:

**OpenAI API**

実装ではOpenAI APIへの依存を業務ロジックから分離するprovider adapterを設ける。MVPのproviderはOpenAI APIで固定し、他providerとの比較は行わない。

AIへ要求する責務:

- 案件全体理解
- candidate抽出
- 不足判定
- 質問バッチ生成
- candidate再評価
- confirmed factからの編纂
- 創作検査

具体的なOpenAIモデル名・versionは、実装時点で利用可能なOpenAI APIモデルの中から、日本語品質、長文理解、構造化出力、速度、コストを確認して選定する。

provider変更は正本改訂を伴う。

### 3.8 資料抽出・OCR

採用:

**Google Cloud Document AI Enterprise Document OCR**

ファイル形式ごとに処理を分ける。

- PDF: テキスト埋込みがあれば直接抽出、画像PDFはDocument AI OCR
- JPEG / PNG: Document AI OCR
- DOCX: 文書parser
- XLSX: 表計算parser
- PPTX: プレゼンテーションparser
- TXT / CSV: 直接読込

Document AI OCRは日本語、印刷文字、手書き文字を扱えるmanaged OCRとして採用する。

OCR / parserは「読めなかった内容を推測しない」を最優先とする。

- 判読不確実な箇所は確定sourceとして扱わない
- 読取警告・要確認範囲を保持する
- 本アプリの代表資料で実装時に精度確認を行う
- 別案件のOCR方式をそのまま流用しない

### 3.9 A4/PDF

採用:

印刷専用HTML/CSS ViewModel + headless Chromium系PDF生成。

方針:

- **A4縦1ページ**
- 1事例を1ページで完結させる
- 画面DOMをそのままPDF化しない
- 正本データから印刷専用ViewModelを生成
- 上部: タイトル、顧客プロフィール、案件要点
- 左カラム: 課題、提案、採用理由、Before/After、成果
- 右カラム: 営業ストーリー、壁と突破、顧客の言葉、横展開ポイント
- 下部: 注意点、公開版・出力版の識別情報
- 情報量が多い場合は文字サイズを極端に縮小せず、表示優先度と要約ルールで1ページに収める
- コメントはA4/PDFへ含めない
- PDF出力元のcompilation/publication versionを追跡可能にする


### 3.9A 添付ファイル上限

MVPの対応形式と上限を次で固定する。

- PDF
- JPG / JPEG
- PNG
- DOCX
- XLSX
- PPTX
- TXT
- CSV
- 1ファイル最大20MB
- 1案件あたり有効添付最大10ファイル
- 1案件あたり最大合計200MB

許可形式外、上限超過、破損ファイルはアップロード前後の検証で明示的に拒否する。

### 3.10 ログ

採用:

- 業務・監査ログ: PostgreSQL
- 技術ログ: Google Cloud Logging

理由:

業務操作の監査履歴はアプリデータと関連付けて保持し、インフラ・障害ログはクラウド側へ分離する。

## 3.11 技術選定の比較結果

| 論点 | 採用 | 主な代替 | 選定理由 |
| --- | --- | --- | --- |
| Web基盤 | TypeScript / Next.js | GAS HTML Service、別SPA+API | PC/スマホUI、型安全、サーバー処理を一体管理しやすい |
| 実行基盤 | Cloud Run | GAS、VM、GKE | コンテナ運用、Cloud SQL/Storage連携、MVPでの運用負荷のバランス |
| DB | Cloud SQL for PostgreSQL | Sheets、Firestore | 関係データ、transaction、履歴、競合、検索をRDBで一貫管理 |
| ファイル | Cloud Storage | DB BLOB、Drive | 大容量バイナリをDBから分離し、アプリ認可と組み合わせやすい |
| 認証 | Google Workspace OIDC | 独自ID/PW | 社内Googleアカウントを利用し、独自パスワード管理を避ける |
| 検索 | Cloud SQL PostgreSQL 18 + pg_bigm | 外部検索、ベクトルDB | 日本語全文検索を同一DBで実現し、MVPの複雑性を抑える |
| PDF | 印刷専用HTML/CSS + headless Chromium | 画面印刷、PDF専用ライブラリ | Web表示と分離したA4レイアウトを管理しやすい |
| AI | OpenAI API + provider adapter | 他provider直結 | MVP providerをOpenAI APIに固定しつつモデル変更を業務ロジックへ波及させない |

## 4. 採用しない構成

### 4.1 GAS + Googleスプレッドシートを中核にしない

理由:

今回のMVPは、

- 多数の関連エンティティ
- transaction
- version競合
- 履歴
- 添付
- OCR
- AI
- 全文検索
- コメント
- PDF
- 監査

を扱う。

GAS/Sheetsを土台にすると、新正本ではなくプラットフォーム都合へ設計を寄せる危険があるため、中核基盤として採用しない。

### 4.2 Firestoreを主DBにしない

本アプリはfact/evidence/version/publication等の関連性と検索条件が多いため、MVPではRDBの方が設計を単純に保ちやすい。

### 4.3 別全文検索サービスをMVPで持たない

MVPはCloud SQL for PostgreSQL 18 + `pg_bigm` で実装する。

代表データでの日本語検索確認は実装受入テストとして扱う。採用方式を実装着手時に再検討しない。

実装中に技術的不成立が確認された場合は、別方式へ独断変更せず工程を停止し、正本変更が必要な重大問題として扱う。

### 4.4 ベクトルDBをMVPで持たない

MVP対象外とする。

## 5. 開発環境

基本方針:

- GitHubを唯一のコード管理場所とする
- TypeScriptの静的検査を必須とする
- 自動テストをCIで実行する
- dev / staging / productionを分離する
- secretをGitへ保存しない
- schema migrationをコード管理する

具体的なCI/CD手段、ORM、テストライブラリ等は実装指示書で指定してよいが、本書の技術構成を変更してはならない。

### 5.1 デプロイ方針

- dev / staging / productionを分離する。
- Claude Codeは実装・自動テスト後に勝手にデプロイしない。
- ChatGPTが正本・差分・テスト結果を検査し、デプロイ可否を判定する。
- ユーザーの明示承認後にのみ、Claude Codeが指定環境へデプロイする。
- 各工程の実機確認はstagingを基本とし、production反映はMVP完了判定後の別承認で行う。
- 認証・権限上Claude Codeが実行できない場合のみ、ChatGPTがユーザーへ具体的な手動操作を依頼する。
- デプロイ先、revision/version、実行者、日時、結果を証跡として残す。

## 8. 結論

新販売事例は、旧GASアプリを作り直すのではなく、新正本に最適なWebアプリとして新規実装する。

中核構成は以下とする。

- TypeScript / Next.js
- Google Cloud Run
- PostgreSQL / Cloud SQL
- Google Cloud Storage
- Google Workspace OIDC
- Cloud SQL for PostgreSQL 18 + 構造化検索 + pg_bigm日本語全文検索
- OpenAI API + provider adapter
- ファイル形式別parser + Google Cloud Document AI OCR
- 印刷専用HTML/CSS + headless Chromium PDF
- PostgreSQL業務監査ログ + Cloud Logging技術ログ

AI provider、OCR、検索基盤、添付上限、A4/PDF方式は本書で確定済みとする。実装時の代表データ確認は採用可否の再検討ではなく受入テストとして扱う。
